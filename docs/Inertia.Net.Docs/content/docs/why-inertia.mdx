## The short version

If you build a React, Vue or Svelte frontend on ASP.NET Core today, you probably have two projects: a Web API that returns JSON, and a single-page app (SPA) that calls it. Inertia lets you keep the modern frontend and drop the second half of that setup.

Your endpoint does not return JSON. It returns the **name of a frontend page** and the **data that page needs**:

```csharp
app.MapGet("/users", (UserStore users) =>
    Render("Users/Index", new InertiaProps { ["users"] = users.All() }));
```

The matching component receives that data as ordinary props:

```tsx
export default function Index({ users }: { users: { id: number; name: string }[] }) {
  return <ul>{users.map((u) => <li key={u.id}>{u.name}</li>)}</ul>
}
```

The first visit is a normal HTML response. After that, links and form submissions fetch the next page's props in the background and swap the component without a full reload. It feels like a SPA, but ASP.NET Core still owns routing, authentication and validation.

**Choose it when** one team ships the frontend and backend together: dashboards, admin tools, SaaS products, internal apps. **Skip it when** you need a public JSON API for mobile apps or third parties, or the frontend is a separate product with its own release cycle.

Want to see it run? Try [First 10 minutes](/docs/first-10-minutes). Want the details? Keep reading.

## In more detail

### Inertia vs a SPA plus a Web API

| | SPA + Web API | Inertia.Net |
|---|---|---|
| Projects to build and deploy | A JSON API and a separate client app, often with different hosts and CORS rules | One ASP.NET Core app that also builds your frontend |
| Routing | A server router for the API and a client router for pages, kept in sync by hand | ASP.NET Core routes only. Each route renders a page |
| Data loading | Fetch calls, loading states and caching in each component | Props arrive with the page. Slow data can be [deferred](/docs/deferred-props) |
| Authentication | Tokens or cookies shared across two apps, plus client-side route guards | Your normal ASP.NET Core cookie auth and `[Authorize]` |
| Validation | Return an error shape from the API and map it to forms in the client | Redirect back with errors, available as `form.errors` ([validation](/docs/validation-and-errors)) |
| API contract | You design, version and document JSON endpoints | The props you pass are the contract. [TypeScript types](/docs/typescript) can be generated |
| Frontend | React, Vue or Svelte | React, Vue or Svelte |

You still write components, hooks and styles. What goes away is the glue: the API layer, the client router, and the code that keeps state in sync with the server.

### Why a .NET developer might like it

- **Minimal APIs, MVC controllers and FastEndpoints stay in charge.** Model binding, authorization, validation attributes and dependency injection work as they always have.
- **One deployment.** `dotnet publish` produces the server and the built frontend assets together.
- **Security defaults you already know.** CSRF protection, cookies and policies are ASP.NET Core's, with [antiforgery wired up](/docs/csrf-and-antiforgery) for you.
- **Pages are real URLs.** Links, refresh, back and bookmarks behave, and optional [server-side rendering](/docs/server-side-rendering) renders the first visit's HTML on the server.

### Prop features

Props are the data a page receives, and most of the performance and user-experience features of Inertia are choices about how a prop is sent.

| Prop type | In C# | What it does | Learn more |
|---|---|---|---|
| Plain | `["title"] = "Hi"` | Sent on every response that includes the key | [Props](/docs/props) |
| Lazy | `Prop(() => ...)` | The loader runs only when the prop is part of the response | [Props](/docs/props) |
| Always | `Always(value)` | Sent even when a partial reload does not ask for it | [Partial reloads](/docs/partial-reloads) |
| Optional | `Optional(() => ...)` | Never sent on the first visit, only when a partial reload asks for it | [Partial reloads](/docs/partial-reloads) |
| Deferred | `Defer(() => ..., group: "stats")` | Left out of the first response, then loaded right away so the page shows up sooner | [Deferred props](/docs/deferred-props) |
| Merge | `Merge(value)`, `DeepMerge(value)` | The client appends or deep merges new data instead of replacing it | [Merging props](/docs/merging-props) |
| Once | `Once(() => ...)` | Resolved once and remembered by the client, with optional expiry | [Once props](/docs/once-props) |
| Infinite scroll | `Scroll(page, ...)` | Merges pages of items and reports paging metadata | [Infinite scroll](/docs/infinite-scroll) |
| Rescued | `.Rescue()` | If its loader throws, the prop is left out and reported in `rescuedProps` instead of failing the whole page | [Props](/docs/props) |
| Parallel | `.Parallel()` | Starts independent async loaders together instead of one after another | [Props](/docs/props) |
| Cached | `.Cache(key, duration)` | Caches a loader's result between requests | [Props](/docs/props) |
| Live | live props | Refresh themselves when the server broadcasts an event, over SignalR or your own transport | [Live props](/docs/live-props) |

Partial reloads let the client ask for only some props (`only` and `except`), so a filter change or a poll does not recompute the whole page. See [Pagination](/docs/pagination) for the numbered and cursor pages that feed pagers and infinite scroll.

### When it is not a good fit

- **You need a public API anyway.** Mobile apps, third-party integrations or several different clients need real JSON endpoints. You can build those next to your Inertia pages, but Inertia will not replace them.
- **The frontend is a separate product.** If another team deploys the frontend on its own schedule, a versioned API is the cleaner boundary.
- **Heavy offline use.** Inertia expects the server for every page change.
- **You want no JavaScript at all.** For server-rendered HTML with a little interactivity, Razor Pages or Blazor may be simpler.

### What it is not

Inertia is not a framework and not a new frontend library. It is a small protocol between your server and the official [Inertia.js](https://inertiajs.com) client, and Inertia.Net is the ASP.NET Core side of it. You keep using React, Vue or Svelte exactly as documented.
