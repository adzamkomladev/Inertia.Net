These releases help you show useful error pages and split long lists into smaller pages. Use the same version of each Inertia.Net package in your app; see [Installation](/docs/installation).

## 1.6.1: show an error page

A visitor who opens a missing URL can see your app's `Error` page while the response still has status 404. In `Program.cs`, add the services and middleware:

```csharp
builder.Services.AddInertia();
builder.Services.AddInertiaErrorPages();

var app = builder.Build();
app.UseInertiaErrorPages();
app.UseInertia();
```

Create an `Error` component in your client pages directory. It receives a `status` prop. Error pages are off in Development by default, so you can see developer diagnostics there. See [Error pages](/docs/error-pages) for a component example and how to preview it.

You can check the status and component in a test using `Inertia.Net.Testing`:

```csharp
using var response = await client.InertiaGetAsync("/missing");
await response.AssertInertiaAsync(page => page.Status(404).Component("Error"));
```

## 1.6.1: return to the previous page

After a form submission, `Back()` normally uses the browser's `Referer` header. Some browser policies omit it. Enable the following in `Program.cs` to remember the last successfully rendered page and use it as a fallback:

```csharp
builder.Services.AddInertia(o => o.State.RememberPreviousUrl = true);
```

The remembered address is shared across tabs in the same browser. See [Previous URL](/docs/redirects-and-history#previous-url) for the fallback order and cookie details.

Inertia forms already retain their input after validation errors. If a full-page form needs to refill a field after a redirect, flash only the safe values you choose; never include passwords or tokens. The [flash data recipe](/docs/flash-data) shows how.

## 1.6.2: send a list one page at a time

For a list already in memory, a Minimal API can bind the requested page and return a numbered result:

```csharp
// posts is an IReadOnlyList<PostDto> in a stable order.
app.MapGet("/posts", (PageRequest request) => Render("Posts/Index", new InertiaProps
{
    ["posts"] = Pagination.Paginate(posts, request),
}));
```

Open `/posts?page=2&perPage=5` to request the second group of five. The result's `data` contains that group; `currentPage` and `lastPage` help build page links. The default size is 20, with a maximum of 100; [pagination options](/docs/configuration#opagination-paginationoptions) can change these limits and query names.

To load more as the reader scrolls, wrap the page in `Scroll(...)` and use the client `InfiniteScroll` component. For data from a database or API, the delegate overload fetches each group on demand. It also supports **cursor pages**: a cursor is a marker used to fetch the next or previous group. Pages can be deferred or cached, and test helpers can load the next or previous scroll page. Follow [Pagination](/docs/pagination), [Infinite scroll](/docs/infinite-scroll), and [Testing](/docs/testing) for examples.

## 1.6.2: page an EF Core query

If your app already uses EF Core, install the optional package alongside your database provider:

```sh
dotnet add package Inertia.Net.EntityFrameworkCore --version 1.6.2
```

For an existing `AppDb` with a `Posts` set, these two calls show the ordering rules:

```csharp
using Inertia.Net;
using Microsoft.EntityFrameworkCore;

// Numbered pages: choose an order first. Id is unique for each post.
var page = await db.Posts.OrderBy(p => p.Id).ToPageAsync(request, ct: ct);

// Cursor pages: leave the query unordered; the helper orders it by Id.
var cursorPage = await db.Posts.ToCursorPageAsync(p => p.Id, cursorRequest, ct: ct);
```

Each result has a `data` array for the current group. A cursor is a marker to send back unchanged to request another group. Choose non-null keys that identify each row uniquely; if several rows share the first key, add a unique second key as a tie-breaker. The [EF Core pagination example](/docs/pagination#with-ef-core) shows how to use the result with `Scroll`. For Native AOT, use the core delegate paginator with an AOT-compatible data source instead.

Treat cursor strings as opaque. They are not tamper-proof; protect them with `IDataProtector` if your app requires tamper protection. An invalid nonempty cursor starts at the first page. When a logger is available, a Debug message records that fallback without the cursor value or exception details; see [Cursors](/docs/pagination#cursors).
