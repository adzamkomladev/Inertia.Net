Props are the data a page receives. `Render(component, props)` takes an `InertiaProps`, a string-keyed dictionary, or a typed object. Inertia.Net walks nested `InertiaProps` and dictionaries, so you can nest props at any depth.

Every page has an `errors` prop. The keys of a page's props come in this order: `errors`, shared props, then page props.

## Choose how to load data

Start with a plain value. Use a lazy loader when the query should run only if the response needs that prop.
Use `Defer` when the page should open before a slow query finishes. Use `Optional` when the data is needed only on request.
`Once` keeps a value on the client across visits. `Cache` keeps a value on the server. They solve different problems.

## Large integer IDs

JavaScript cannot represent every 64-bit integer exactly. Set `o.PreserveBigIntegers = true` at registration to wrap unsafe
integers as `$bigint` markers. The v3 client reads the markers as `BigInt`. The default is false.
To override that choice for one page, return `Render("Orders/Show", props).PreserveBigIntegers()` or
`.PreserveBigIntegers(false)`. Props and flash use the same setting. This is a handler fragment.

**C# 15 unions (.NET 11).** A prop can have a `union` type, for example `public union Subject(User, Team);`. Inertia.Net writes such a prop as the JSON of its active case, with no wrapper or discriminator, through your source-generated `JsonSerializerContext`. Partial reloads select it like any other prop. Inertia.Net does not resolve an `InertiaProp` (`Defer`, `Optional`, ...) stored inside a union case, so keep lazy props at the page level.

## The prop factories

| C\# | Behavior |
|---|---|
| `["title"] = "Hi"` | A plain value. Sent on every response that includes the key. |
| `Prop(() => ...)` | Lazy: the loader runs only when the prop is part of the response. |
| `Always(value)` or `Always(() => ...)` | Sent even when a partial reload does not ask for it. |
| `Optional(() => ...)` | Never sent on the first visit, only when a partial reload asks for it. |
| `Defer(() => ..., group: "name")` | Left out of the first response. The client loads it right away with its group. |
| `Merge(value)` | The client appends the new value to its current one. |
| `DeepMerge(value)` | The client deep merges the value. |
| `Once(() => ...)` | Resolved once and remembered by the client. |
| `Scroll(page, wrapper: "data", metadata)` | An infinite-scroll prop with paging metadata. |

Every lazy factory (`Prop`, `Always`, `Optional`, `Defer`, `Merge`, `DeepMerge`, `Once`, `Scroll`) accepts five loader shapes:

```csharp
Prop(() => value)                                  // Func<T>
Prop(() => repo.GetAsync())                        // Func<Task<T>>
Prop(() => repo.GetValueTaskAsync())               // Func<ValueTask<T>>
Prop(ct => repo.GetAsync(ct))                      // Func<CancellationToken, Task<T>>
Prop(ct => repo.GetValueTaskAsync(ct))             // Func<CancellationToken, ValueTask<T>>
```

The cancellation token a loader receives is `HttpContext.RequestAborted`. An `async` lambda always binds to the awaiting overload, never to “a prop whose value is a Task”.

Fluent methods mutate and return the same instance: `.Once(key?, until?)`, `.As(key)`, `.Until(ttl)`, `.Fresh()`, `.Append(path?, matchOn?)`, `.Prepend(path?, matchOn?)`, `.DeepMerge()`, `.MatchOn(params keys)`, `.Defer(group)`, `.WithGroup(group)`, `.Rescue()`, `.Timeout(timeout)`, `.Parallel()`, `.Cache(key, duration)` and `.Cache(key, duration, staleFor?, tags?)`.

`Fresh()` makes a prop a once prop, and `WithGroup()` makes it deferred. Repeated `MatchOn()` calls add keys. Root `Append()` and `Prepend()` are mutually exclusive, and combining them throws. Fluent methods mutate the prop, so create prop instances per request. Do not share prop instances across requests.

## Resolution order

By default, loaders run one after another, in prop order. A loader runs only when its prop is included in the response. Because loaders run one at a time, a scoped EF Core `DbContext` is safe to use in several loaders.

```csharp
return Render("Users/Index", new InertiaProps
{
    ["title"] = "Users",
    ["users"] = Prop(ct => db.Users.ToListAsync(ct)),
    ["filters"] = Always(new { search = "ann" }),
});
```

```json
{
  "component": "Users/Index",
  "props": { "errors": {}, "title": "Users", "users": [ { "id": 1, "name": "Ann" } ], "filters": { "search": "ann" } },
  "url": "/users?search=ann",
  "version": "3f9a1c0d5b7e2a64c8d1e0f9b3a57c21",
  "sharedProps": ["errors"]
}
```

Inertia.Net buffers the page before sending it, so a loader that throws never produces a half-written `200`.

### Parallel props

Mark independent async loaders with `.Parallel()` to start them together:

```csharp
return Render("Dashboard", new InertiaProps
{
    ["stats"] = Prop(ct => statsService.GetAsync(ct)).Parallel(),
    ["activity"] = Defer(ct => activityService.RecentAsync(ct)).Parallel(),
    ["user"] = currentUser, // values and sync loaders resolve in turn
});
```

- Only `Task` and `ValueTask` loaders can be parallel. `Parallel()` throws for values and synchronous loaders.
- At most `InertiaOptions.Props.MaxConcurrency` loaders run at once per render. The default is 4.
- Top-level props and props inside literal objects (`InertiaProps` and other string-keyed dictionaries) start early. Parallel props anywhere else resolve in turn.
- Loaders of props that are not part of the response never start.
- If a loader fails, Inertia.Net cancels and awaits the others. The render then fails with the first failure in prop order. A `Rescue()`d prop fails alone.

<Callout type="warning" title="DbContext and HttpContext">
A parallel loader must not use the request's `DbContext` or other non-thread-safe scoped services, and must not touch `HttpContext`. Give each loader its own context through `IDbContextFactory<T>` or its own scope. The build warns about it: [INERTIA003](/docs/page-records#compile-time-component-checks) reports a `Parallel()` loader that captures an `HttpContext` or a `DbContext` from outside the lambda.
</Callout>

```csharp
["orders"] = Prop(async ct =>
{
    await using var db = await dbFactory.CreateDbContextAsync(ct);
    return await db.Orders.CountAsync(ct);
}).Parallel(),
```

### Scoped services in loaders

`Prop<TService, T>(...)` hands a loader a service from the request, without capturing it in a closure:

```csharp
["orders"] = Prop<AppDbContext, int>((db, ct) => db.Orders.CountAsync(ct)),
["inbox"] = Prop<InboxService, Inbox>((inbox, ct) => inbox.LoadAsync(ct)).Defer(), // and .Once(), .Cache(...), .Live(...), .Rescue()
```

- A loader that runs during the request gets the request's instance. This is the same `DbContext` the handler used.
- A `.Parallel()` loader gets a scope of its own, so two parallel loaders never share a `DbContext`. The scope is disposed when the loader finishes.
- A [stale-while-revalidate](#cached-props) refresh runs after the response, in a new scope. That scope is disposed when the refresh ends.
- If the service is not registered, the render fails with the prop's path and the service type.

## Deferred props

`Defer` leaves the prop out of the first response and lists it under `deferredProps`. The client asks for each group as soon as the page is mounted.

```csharp
["stats"] = Defer(ct => stats.GetAsync(ct)),                 // group "default"
["feed"]  = Defer(ct => feed.GetAsync(ct), group: "sidebar"),
```

```json
{ "props": { "errors": {} }, "deferredProps": { "default": ["stats"], "sidebar": ["feed"] } }
```

See [Deferred props](/docs/deferred-props) for the client component and the request rules.

## Merge props

```csharp
["posts"]    = Merge(posts),                                  // append
["messages"] = Prop(() => messages).Prepend(),                // prepend
["settings"] = DeepMerge(settings),
["rows"]     = Merge(rows).MatchOn("id"),                     // replace items with the same id
["chat"]     = Merge(chat).Append("messages", matchOn: "id"), // append at a nested path
```

```json
{
  "mergeProps": ["posts", "chat.messages"],
  "prependProps": ["messages"],
  "deepMergeProps": ["settings"],
  "matchPropsOn": ["rows.id", "chat.messages.id"]
}
```

The full behavior is in [Merging props](/docs/merging-props).

## Once props

```csharp
["plans"] = Once(ct => plans.AllAsync(ct)).Until(TimeSpan.FromHours(1)).As("billing-plans"),
```

```json
{
  "props": { "errors": {}, "plans": [ { "id": "pro" } ] },
  "onceProps": { "billing-plans": { "prop": "plans", "expiresAt": 1760000000000 } }
}
```

When the client already holds the key, it sends `X-Inertia-Except-Once-Props`. The value is then left out, and the `onceProps` entry stays. See [Once props](/docs/once-props).

## Cached props

`.Cache(key, duration)` keeps a prop's value as JSON in the cache. The default cache is the app's `IMemoryCache`. A cache hit costs neither the query nor serialization.

```csharp
return Render("Dashboard", new InertiaProps
{
    ["stats"] = Prop(ct => stats.ComputeAsync(ct)).Cache("dashboard-stats", TimeSpan.FromMinutes(5)),
    ["orders"] = Defer(ct => orders.RecentAsync(userId, ct)).Cache($"orders:{userId}", TimeSpan.FromMinutes(1), tags: [$"user:{userId}"]),
    ["catalog"] = Optional(() => catalog.All()).Cache("catalog", TimeSpan.FromHours(1), staleFor: TimeSpan.FromHours(23)),
});
```

<Callout type="important" title="The key is the value's identity">
Every request that uses a key gets the same value. Put the user, tenant or anything else the value depends on in the key. Keys live in their own cache space and cannot collide with the app's own entries.
</Callout>

The cached value must be plain data. `Cache(...)` on a loader that returns an `InertiaProp`, such as `Prop(() => Defer(...)).Cache(...)`, is reported at build time by [INERTIA004](/docs/page-records#compile-time-component-checks). Cache the inner prop instead.

Caching only changes how a prop loads. Optional, deferred, merged, once and scroll props keep their behavior, and their metadata is written from the cache too. A parallel cached prop does not start its loader on a cache hit. A rescued failure is not cached.

**Removing and replacing values.** Inject `IInertiaCache` where the data changes:

```csharp
app.MapPost("/orders", async (OrderInput input, IInertiaCache cache, CancellationToken ct) =>
{
    var order = await orders.CreateAsync(input, ct);
    await cache.RemoveByTagAsync($"user:{order.UserId}", ct);
    await cache.RemovePropAsync("dashboard-stats", ct);
    await cache.SetPropAsync("catalog", await catalog.AllAsync(ct), TimeSpan.FromHours(1), cancellationToken: ct);
    return Back();
});
```

`ClearPropsAsync()` removes every cached prop. `ClearSsrAsync()` removes every cached render. `SetPropAsync` serializes the value the way a prop of that type is serialized, and takes the same `staleFor` and `tags`.

The default store keeps cached props in the app's `IMemoryCache`, with no size limit of their own. Set `o.Props.CacheMaxBytes` to cap them. Cached props then go in a private cache, and the least recently used ones are evicted past the cap.

**Stale-while-revalidate.** `staleFor` keeps serving a value after its duration. The first request that reads a stale value gets the stale value at once, and the loader runs after the response has been sent. After `duration + staleFor`, the loader runs during the request again.

- When the response completes, Inertia.Net queues the refreshes on a bounded background worker. The response does not wait for the loader. Loaders that use `staleFor` must use singleton dependencies, or create an independent scope inside the loader with `IServiceScopeFactory.CreateAsyncScope()` or `IDbContextFactory<T>`. Do not capture request-scoped services or `HttpContext`. [INERTIA003](/docs/page-records#compile-time-component-checks) reports a `staleFor` loader that captures an `HttpContext` or a `DbContext`.
- The worker accepts 64 pending refreshes and runs up to 4 at a time. It cancels each refresh after 30 seconds, and cancels all of them on host shutdown. When the queue is full, Inertia.Net drops the refresh and logs a warning. The stale value keeps its existing expiration. Monitor `inertia.cache.refresh.dropped`, tagged with `inertia.cache.kind=prop|ssr`.
- One refresh runs per key and app instance at a time. A refresh that finds the value fresh again skips its loader.
- An `IInertiaCache` removal (`RemovePropAsync`, `RemoveByTagAsync`, `ClearPropsAsync`) can happen while a fill or refresh is running. If the loader started before the removal of its key or of one of its tags, on the same app instance, the fill or refresh does not store its value. The request still gets the value. Removing another key or tag does not affect the fill or refresh.
- A refresh that fails is logged as a warning, and the stale value stays. The next stale read tries again.

**Another store.** Props and SSR renders live in an `IInertiaCacheStore`. Register your own singleton before or after `AddInertia()`:

```csharp
builder.Services.AddSingleton<IInertiaCacheStore, MyRedisInertiaCacheStore>();
```

The store gets and sets byte arrays by `InertiaCacheKey`, removes by key and by tag, and reads unknown formats as a miss. While a page renders, a store that throws is logged, at most once every 30 seconds, and counts as a miss. `IInertiaCache` lets the exception through.

For a store shared by every app instance, `Inertia.Net.Redis` registers one with `AddInertiaRedisCache(...)`. See [Redis cache](/docs/redis).

## Typed page props

A typed object is AOT-friendly. Inertia.Net walks the object through its `JsonTypeInfo`. It resolves members of type `InertiaProp`, and the rest is serialized normally.

```csharp
public sealed class UsersPage
{
    public required IReadOnlyList<UserDto> Users { get; init; }
    public required InertiaProp Stats { get; init; }        // resolved by Inertia.Net
}

app.MapGet("/users", (AppDb db) => Render("Users/Index", new UsersPage
{
    Users = db.Users.Select(u => new UserDto(u.Id, u.Name)).ToList(),
    Stats = Defer(ct => db.StatsAsync(ct)),
}));
```

Under Native AOT, register `UsersPage` and its value types in your `JsonSerializerContext`. Anonymous types work only when reflection-based serialization is enabled, so they do not work under AOT.

## Dot keys

A top-level key containing dots is unpacked. `["user.name"] = "Ann"` becomes `"user": { "name": "Ann" }`. Cached props under dot keys use the cache too.

## BigInteger safety

With `o.PreserveBigIntegers = true`, integers beyond ±(2^53 − 1) are written as `{"$bigint":"9007199254740993"}` and the page gets `"preserveBigIntegers": true`.

```csharp
builder.Services.AddInertia(o => o.PreserveBigIntegers = true);
```

## Rescue

`.Rescue()` keeps a page alive when one prop fails:

```csharp
["recommendations"] = Defer(ct => recs.GetAsync(ct)).Rescue(),
```

If the loader throws, Inertia.Net logs the exception and leaves the prop out of `props`. The prop's path goes to `"rescuedProps": ["recommendations"]`. Without `.Rescue()`, the exception propagates normally. Cancellation of the request is never rescued.

## Timeout

`.Timeout(TimeSpan)` bounds a loader. When the time is up, the loader's cancellation token is cancelled and the render stops waiting for it, so a loader that ignores the token does not hold the request either:

```csharp
["recommendations"] = Defer(ct => recommender.ForAsync(userId, ct)).Timeout(TimeSpan.FromSeconds(2)).Rescue(),
["stats"] = Prop(ct => stats.ComputeAsync(ct)).Parallel().Timeout(TimeSpan.FromSeconds(5)),
```

- With `Rescue()` the prop is left out and listed in `rescuedProps`, like any rescued failure.
- Without it the render fails with a `TimeoutException`, as for any loader exception.
- It works on sequential and `Parallel()` loaders, on cache misses and on stale-while-revalidate refreshes.
- A synchronous loader cannot be interrupted: it finishes before the timeout is checked.
