ForgetMeNot is a small todo app. It is small, but it uses the same pieces as a real product: sign-in, private data, a public page, a long list that loads as you scroll, and a reminder that appears on your screen without a refresh.

Each step tells you **what** to do and **why**. If you know why a line is there, you can change it later without fear.

<Callout type="info" title="What you need">
- The .NET 10 or .NET 11 SDK
- Bun, npm, pnpm or Yarn. The commands use Bun; swap in your own.
- A code editor and a terminal

You do not need a database server. The app uses SQLite, a database that lives in one file.
</Callout>

## What you will build

Every feature below is here because it shows one idea from Inertia.Net. The right column says which one.

| You build | You learn |
|---|---|
| Sign in with a cookie | The `--auth` starter, redirects to the login page, and a sign-in rate limit |
| A page of lists | Page records, named routes and the typed `routes.ts` file |
| A form that checks itself | Precognition: the server validates a field as you type |
| Slow numbers that load after the page | Deferred props, plus a cache you clear when data changes |
| A list with thousands of items | `ToPageAsync` and infinite scroll |
| A link anyone can open | Server-side rendering and the SSR cache |
| A reminder that shows up by itself | Live props over SignalR |
| Tests | `Inertia.Net.Testing` |

## 1. Create the app

Install the templates once, then create the app. `--auth` adds cookie sign-in, so you do not write that yourself. Use `--framework vue` or `--framework svelte` for the other clients, and pick the matching tab in the examples below.

```sh
dotnet new install Inertia.Net.Templates::1.9.2
dotnet new inertia -n ForgetMeNot --framework react --auth
cd ForgetMeNot
bun install
```

Start the two development processes and keep both terminals open:

```sh
# terminal 1: the frontend (Vite)
bun run dev

# terminal 2: the backend
dotnet watch
```

Open `http://localhost:5180`, click **Log in**, and sign in with `demo@example.com` and the password `password`. Click around before you change anything.

<Callout type="info" title="Why two processes?">
Vite serves your React, Vue or Svelte code and reloads it the moment you save. ASP.NET Core serves the pages. While Vite runs, it writes a small file called `wwwroot/hot`, and the app uses it to find Vite. Nothing else is needed.
</Callout>

The template is not empty. It already uses the features we want, and it is worth knowing where they are:

| Where | What it does | Why it matters |
|---|---|---|
| `HomePage`, `LoginPage` in `Program.cs` | **Page records.** A record that names its component once: `Component => "Home"` | The props and the page name stay together, and the compiler checks them |
| `.WithName("login")` on each route | **Named routes** | A name is a stable handle for a URL. You can change the URL and nothing breaks |
| `ClientApp/types/routes.ts` | **Typed routes**, written from the names | In the browser you write `routes.login()`, never the string `"/login"` |
| `ClientApp/types/inertia.d.ts` | TypeScript types for every page, written from the C# records | A renamed property is a compile error, not a blank spot on the page |
| `.WithInertiaPrecognition()` on the login | The form checks a field on the server when you leave it | One set of rules, run in the browser and on the server |
| `AddInertiaErrorPages()` | A 404 or 500 shows your `Error` page | Visitors never see a raw error |

Both generated files are rewritten when the app starts in Development. You never edit them by hand.

## 3. Add a database

Lists and items must survive a restart, so they need a database. We use **EF Core with SQLite**: EF Core is the usual way to talk to a database from C#, and SQLite needs no server.

```sh
dotnet add package Microsoft.EntityFrameworkCore.Sqlite --version "10.*"
dotnet add package Inertia.Net.EntityFrameworkCore --version 1.9.2
```

<Callout type="tip" title="On .NET 11?">
Use `--version "11.*"` for the SQLite package. The EF Core version must match your .NET version.
</Callout>

Create `Data.cs`. These classes are the **database shape**. They are not what the browser sees; that comes next.

```csharp
using Microsoft.EntityFrameworkCore;

namespace ForgetMeNot;

public sealed class TodoList
{
    public int Id { get; set; }
    public required string OwnerEmail { get; set; }
    public required string Title { get; set; }

    /// <summary>The secret part of the public URL. Null while the list is private.</summary>
    public string? ShareSlug { get; set; }

    public List<TodoItem> Items { get; } = [];
}

public sealed class TodoItem
{
    public int Id { get; set; }
    public int TodoListId { get; set; }
    public TodoList List { get; set; } = null!;
    public required string Title { get; set; }
    public bool IsDone { get; set; }

    // / <summary>When to remind the owner, in UTC. Null means no reminder. (A DateTime, not a
    // DateTimeOffset: SQLite cannot compare those in a query.)</summary>
    public DateTime? RemindAt { get; set; }

    /// <summary>Set once the reminder has fired, so a restart never sends it twice.</summary>
    public DateTime? RemindedAt { get; set; }
}

public sealed class AppDb(DbContextOptions<AppDb> options) : DbContext(options)
{
    public DbSet<TodoList> Lists => Set<TodoList>();
    public DbSet<TodoItem> Items => Set<TodoItem>();

    protected override void OnModelCreating(ModelBuilder model)
    {
        model.Entity<TodoList>().HasIndex(l => l.OwnerEmail);
        model.Entity<TodoList>().HasIndex(l => l.ShareSlug).IsUnique();
    }
}
```

A few choices are worth explaining:

- **`OwnerEmail` instead of a users table.** The template's demo user already has an email in the sign-in cookie. Using it as the owner key keeps this guide short. In a real app you would use ASP.NET Core Identity and a user id.
- **`ShareSlug` is null until you share.** A random secret in the URL is the only thing that opens a public list. There is nothing to guess, and turning sharing off simply forgets the secret.
- **`RemindedAt` makes reminders safe to repeat.** If the app restarts halfway through, a reminder that was already sent is never sent twice.
- **`DateTime`, not `DateTimeOffset`, for reminders.** SQLite cannot compare `DateTimeOffset` values inside a query. We store UTC times as plain `DateTime`, and the query `RemindAt <= now` works.

Now open `Program.cs`. First, **delete the demo todo code** that came with the template. We replace it with our own:

- the `AddSingleton<TodoStore>()` line
- the `/todos` endpoints (the ones named `todos.index`, `todos.store`, `todos.toggle` and `todos.destroy`)
- the `/dashboard` endpoint and the `DashboardPage` record
- the `Todo`, `TodoStats`, `TodosPage`, `NewTodo` and `TodoStore` types
- their lines in `AppJsonContext` at the bottom

Then register the database where the other services are registered:

```csharp
using Microsoft.EntityFrameworkCore; // at the top of the file

builder.Services.AddDbContext<AppDb>(o =>
    o.UseSqlite(builder.Configuration.GetConnectionString("Default") ?? "Data Source=forgetmenot.db"));
```

And create the tables right after `var app = builder.Build();`:

```csharp
using (var scope = app.Services.CreateScope())
{
    // fine for a first app; use migrations later
    scope.ServiceProvider.GetRequiredService<AppDb>().Database.EnsureCreated();
}
```

<Callout type="info" title="Why read the connection string from configuration?">
Production and tests need a different database than your laptop. With `GetConnectionString("Default")` they can set `ConnectionStrings:Default` without touching the code. We use this in the tests.
</Callout>

`EnsureCreated()` builds the tables on the first run. It cannot change them later. When the model changes in a real app, switch to EF Core migrations.

## 4. Decide what the browser sees

Never send a database entity to the browser. It may have columns you did not mean to share (like `OwnerEmail`), and every change to the table would change your page. Send small **records** that hold only what a page needs.

Create `Models.cs`:

```csharp
using System.ComponentModel.DataAnnotations;
using System.Security.Claims;

namespace ForgetMeNot;

// What the browser receives: small records, never the database entities.

public sealed record ListCard(int Id, string Title, int Open, int Total, bool IsShared);
public sealed record Stats(int Open, int Done);
public sealed record ReminderRow(int Id, int ListId, string Title, DateTime RemindAt);
public sealed record ListHeader(int Id, string Title, bool IsShared, string? ShareUrl);
public sealed record ItemRow(int Id, string Title, bool IsDone, DateTime? RemindAt);
public sealed record PublicHeader(string Title, int Open);
public sealed record PublicItem(int Id, string Title);

// What the browser sends. These are public classes because the AddValidation() generator skips internal
// types.

public sealed class NewList
{
    [Required, StringLength(80)]
    public string? Title { get; set; }
}

public sealed class NewItem
{
    [Required, StringLength(200)]
    public string? Title { get; set; }

    public DateTime? RemindAt { get; set; }
}

// / <summary>An event name plus the channel it travels on. The page and the publisher both use this one
// value.</summary>
public static class Events
{
    public static LiveEvent RemindersChanged(string email) => new("RemindersChanged", LiveChannel.Private($"users.{email}"));
}

public static class UserExtensions
{
    /// <summary>The signed-in person's email: our key for "whose list is this?".</summary>
    public static string Email(this ClaimsPrincipal user) => user.FindFirstValue(ClaimTypes.Email)!;
}
```

Three things here are easy to miss:

- **Form classes are `public`.** The validation generator, `AddValidation()`, skips `internal` types. A private form class means the `[Required]` rules silently do nothing.
- **`Events.RemindersChanged(email)` is one value used twice.** The page uses it to say "refresh me when this happens", and the worker uses it to say "this happened". Because both use the same value, they cannot drift apart.
- **`Email()` hides one claim lookup.** Every endpoint asks the same question, "whose list is this?", so we ask it in one place.

The template turned off reflection-based JSON, which keeps the app ready for Native AOT. The price is that you list every type that goes to or from the browser. Add these lines to `AppJsonContext` at the bottom of `Program.cs`:

```csharp
[JsonSerializable(typeof(ListCard))]
[JsonSerializable(typeof(Stats))]
[JsonSerializable(typeof(List<ReminderRow>))]
[JsonSerializable(typeof(Page<ItemRow>))]
[JsonSerializable(typeof(Page<PublicItem>))]
[JsonSerializable(typeof(NewList))]
[JsonSerializable(typeof(NewItem))]
```

Each page record gets its own line when you create it: `ListsPage` in step 5, `ListPage` in step 6 and `PublicPage` in step 7.

<Callout type="tip" title="Forgot one?">
You get an error the first time that type is sent, and the message names the type. Add it and try again.
</Callout>

## 5. The lists page

A **page record** holds the props of a page and also the code that fills them. Create `ListsPage.cs`:

```csharp
using System.Security.Claims;
using Microsoft.EntityFrameworkCore;

namespace ForgetMeNot;

public sealed record ListsPage(
    List<ListCard> Lists,
    [property: InertiaPropType(typeof(Stats))] InertiaProp Stats,
    [property: InertiaPropType(typeof(List<ReminderRow>))] InertiaProp Reminders) : IInertiaPage
{
    public static string Component => "Lists/Index";

    public static async Task<IResult> Handle(ClaimsPrincipal user, AppDb db, CancellationToken ct)
    {
        var email = user.Email();

        var lists = await db.Lists.AsNoTracking()
            .Where(l => l.OwnerEmail == email)
            .OrderBy(l => l.Title)
            .Select(l => new ListCard(l.Id, l.Title, l.Items.Count(i => !i.IsDone), l.Items.Count, l.ShareSlug != null))
            .ToListAsync(ct);

        return Render(new ListsPage(
            lists,
            // Slow part: sent after the page shows. Cached per person, and cleared by tag whenever their
            // data changes.
            Defer(c => LoadStats(db, email, c))
                .Cache($"stats:{email}", TimeSpan.FromMinutes(5), tags: [$"user:{email}"]),
            // Refreshes by itself when the reminder worker publishes this event.
            Defer(c => LoadReminders(db, email, c)).Live(Events.RemindersChanged(email))));
    }

    private static async Task<Stats> LoadStats(AppDb db, string email, CancellationToken ct) =>
        new(await db.Items.CountAsync(i => i.List.OwnerEmail == email && !i.IsDone, ct),
            await db.Items.CountAsync(i => i.List.OwnerEmail == email && i.IsDone, ct));

    private static Task<List<ReminderRow>> LoadReminders(AppDb db, string email, CancellationToken ct) =>
        db.Items.AsNoTracking()
            .Where(i => i.List.OwnerEmail == email && i.RemindedAt != null && !i.IsDone)
            .OrderByDescending(i => i.Id)
            .Take(10)
            .Select(i => new ReminderRow(i.Id, i.TodoListId, i.Title, i.RemindAt!.Value))
            .ToListAsync(ct);
}
```

Add `[JsonSerializable(typeof(ListsPage))]` to `AppJsonContext`, then read the handler from top to bottom:

1. `lists` is read straight from the database into `ListCard` records. `AsNoTracking()` tells EF Core we will not change these rows, which makes the query cheaper.
2. `Stats` is **deferred**. The page is sent right away and the browser asks for the numbers a moment later. The visitor sees the page sooner, even if counting is slow.
3. `.Cache(...)` keeps the finished stats for five minutes, so a second visit does not count again. The `tags` give us a way to throw them away: every write will remove the tag `user:email`, so the numbers are never wrong for long.
4. `Reminders` is deferred and **live**. We come back to it in step 8.

Now the routes. Create `Endpoints.cs`:

```csharp
using System.Security.Claims;
using Microsoft.EntityFrameworkCore;

namespace ForgetMeNot;

public static class ForgetMeNotEndpoints
{
    public static void MapForgetMeNot(this IEndpointRouteBuilder app)
    {
        // Everything in this group needs a signed-in person. The cookie handler sends everyone else to
        // /login.
        var signedIn = app.MapGroup("").RequireAuthorization();

        // Each .WithName(...) gives the route a typed function in ClientApp/types/routes.ts.
        signedIn.MapGet("/lists", ListsPage.Handle).WithName("lists.index");

        signedIn.MapPost("/lists", async (
            NewList input, ClaimsPrincipal user, AppDb db, IInertiaCache cache, CancellationToken ct) =>
        {
            var list = new TodoList { OwnerEmail = user.Email(), Title = input.Title!.Trim() };
            db.Lists.Add(list);
            await db.SaveChangesAsync(ct);
            // the cached stats are out of date now
            await cache.RemoveByTagAsync($"user:{user.Email()}", ct);
            return Results.Redirect($"/lists/{list.Id}");
        }).WithInertiaPrecognition().WithName("lists.store");
    }
}
```

Call it from `Program.cs`, in the place where the `/dashboard` endpoint used to be:

```csharp
app.MapForgetMeNot(); // our lists, items and the public page
```

Also send people to their lists after they sign in. In the `/login` endpoint, change the last `"/dashboard"` to `"/lists"`.

<Callout type="info" title="Why these routes have names">
`.WithName("lists.store")` costs nothing, and it pays you back twice. The name becomes `routes.lists.store()` in your frontend, so you never type `"/lists"` again. And the form's type, `RouteBodies['lists.store']`, is taken from the C# class `NewList`, so the C# and the TypeScript cannot disagree.
</Callout>

<Callout type="info" title="Why .WithInertiaPrecognition()?">
It does two jobs. A normal submit with bad data is sent back to the form with the error messages. And when the page asks, "is this one field valid?" while the person is still typing, the server answers without running your code. You write the rules once, on the class, with `[Required]` and `[StringLength]`.
</Callout>

## 6. One list, with infinite scroll

A list can have thousands of items. Sending them all would make the page slow, so we send one page of items and the browser asks for the next page when the reader scrolls to the end.

Create `ListPage.cs`, and add `[JsonSerializable(typeof(ListPage))]` to `AppJsonContext`:

```csharp
using System.Security.Claims;
using Microsoft.EntityFrameworkCore;

namespace ForgetMeNot;

public sealed record ListPage(
    ListHeader List,
    [property: InertiaPropType(typeof(Page<ItemRow>))] InertiaProp Items) : IInertiaPage
{
    public static string Component => "Lists/Show";

    public static async Task<IResult> Handle(
        int id, PageRequest request, ClaimsPrincipal user, AppDb db, LinkGenerator links, CancellationToken ct)
    {
        var email = user.Email();

        var row = await db.Lists.AsNoTracking()
            // another person's list looks like a missing one
            .Where(l => l.Id == id && l.OwnerEmail == email)
            .Select(l => new { l.Id, l.Title, l.ShareSlug })
            .FirstOrDefaultAsync(ct);
        if (row is null) return Results.NotFound();

        // Named routes work on the server too: ask the link generator for the public address of this list.
        var shareUrl = row.ShareSlug is null ? null : links.GetPathByName("public.show", new { slug = row.ShareSlug });
        var list = new ListHeader(row.Id, row.Title, row.ShareSlug is not null, shareUrl);

        // ToPageAsync adds Skip/Take and counts the rows. A unique order (Id last) keeps pages from
        // overlapping.
        var items = await db.Items.AsNoTracking()
            .Where(i => i.TodoListId == id)
            .OrderBy(i => i.IsDone).ThenBy(i => i.Id)
            .Select(i => new ItemRow(i.Id, i.Title, i.IsDone, i.RemindAt))
            .ToPageAsync(request, ct: ct);

        return Render(new ListPage(list, Scroll(items)));
    }
}
```

- **`.ToPageAsync(request)`** (from `Inertia.Net.EntityFrameworkCore`) adds `Skip` and `Take` for you and counts the rows. `PageRequest` reads `?page=2` from the URL by itself.
- **The order must be unique.** We sort by `IsDone` and then by `Id`. If two items could tie, a row might appear on two pages or on none.
- **`Scroll(items)`** tells the browser that this value is a list that grows. New pages are merged into `items.data` instead of replacing it.
- **Someone else's list is a 404.** The query asks for the id and the owner together. It does not reveal that the list exists.
- **`links.GetPathByName("public.show", ...)`** is a named route used on the **server**. The page needs the public address, and the name builds it, so the URL pattern lives in one place only. (The route is added in step 7, until then the address is simply empty.)

Add the rest of the routes inside `MapForgetMeNot`, after the two list routes. Add `using System.Security.Cryptography;` at the top of the file too:

```csharp
signedIn.MapGet("/lists/{id:int}", ListPage.Handle).WithName("lists.show");

signedIn.MapPost("/lists/{id:int}/items", async (
    int id, NewItem input, ClaimsPrincipal user, AppDb db, IInertiaCache cache, CancellationToken ct) =>
{
    if (!await db.Lists.AnyAsync(l => l.Id == id && l.OwnerEmail == user.Email(), ct)) return Results.NotFound();

    db.Items.Add(new TodoItem { TodoListId = id, Title = input.Title!.Trim(), RemindAt = input.RemindAt });
    await db.SaveChangesAsync(ct);
    await cache.RemoveByTagAsync($"user:{user.Email()}", ct);
    return Back($"/lists/{id}").WithFlash("success", "Added");
}).WithInertiaPrecognition().WithName("items.store");

signedIn.MapPatch("/items/{id:int}/toggle", async (
    int id, ClaimsPrincipal user, AppDb db, IInertiaCache cache, CancellationToken ct) =>
{
    var item = await db.Items.FirstOrDefaultAsync(i => i.Id == id && i.List.OwnerEmail == user.Email(), ct);
    if (item is null) return Results.NotFound();

    item.IsDone = !item.IsDone;
    await db.SaveChangesAsync(ct);
    await cache.RemoveByTagAsync($"user:{user.Email()}", ct);
    return Back($"/lists/{item.TodoListId}");
}).WithName("items.toggle");

signedIn.MapDelete("/items/{id:int}", async (
    int id, ClaimsPrincipal user, AppDb db, IInertiaCache cache, CancellationToken ct) =>
{
    var item = await db.Items.FirstOrDefaultAsync(i => i.Id == id && i.List.OwnerEmail == user.Email(), ct);
    if (item is null) return Results.NotFound();

    db.Items.Remove(item);
    await db.SaveChangesAsync(ct);
    await cache.RemoveByTagAsync($"user:{user.Email()}", ct);
    return Back($"/lists/{item.TodoListId}").WithFlash("success", "Deleted");
}).WithName("items.destroy");

// Turn sharing on (make a secret link) or off (forget it, so the old link stops working).
signedIn.MapPost("/lists/{id:int}/share", async (
    int id, ClaimsPrincipal user, AppDb db, CancellationToken ct) =>
{
    var list = await db.Lists.FirstOrDefaultAsync(l => l.Id == id && l.OwnerEmail == user.Email(), ct);
    if (list is null) return Results.NotFound();

    list.ShareSlug = list.ShareSlug is null ? Convert.ToHexString(RandomNumberGenerator.GetBytes(8)).ToLowerInvariant() : null;
    await db.SaveChangesAsync(ct);
    return Back($"/lists/{id}");
}).WithName("lists.share");
```

Notice the pattern. Each write **checks the owner in the query**, **saves**, **clears the stats cache**, and **sends the person back** with `Back(...)`. `Back` returns them to the page they came from, so the page shows the new state, and `WithFlash` carries the one-time message.

<Callout type="warning" title="Do not forget the owner check">
`GET /lists/5` is protected, but `PATCH /items/9` is a separate door. Every endpoint that takes an id must check that the id belongs to the signed-in person. This is the most common security bug in apps like this one.
</Callout>

Sharing works like this: the first press creates a random secret, and the second press forgets it. Eight random bytes are 16 characters nobody can guess. Do not use `Random` or a counter for a secret.

## 7. Share a list, and render it on the server

A shared list is a page that anyone can open, and many people may open the same one. That makes it the perfect page for **server-side rendering (SSR)**.

Without SSR, the server sends an empty page and the browser has to download JavaScript, run it, and only then show the list. With SSR, the server runs your component first and sends finished HTML. Search engines and slow phones get the content at once, and the browser then "wakes up" the page with the same code.

The share button already exists, from step 6. All that is missing is the page it points to.

Create `PublicPage.cs`, add `[JsonSerializable(typeof(PublicPage))]` to `AppJsonContext`, and map the route:

```csharp
// inside MapForgetMeNot, at the end. No sign-in here: anyone with the link can read the list.
app.MapGet("/p/{slug}", PublicPage.Handle).WithName("public.show");
```

The page record:

```csharp
using Microsoft.EntityFrameworkCore;

namespace ForgetMeNot;

public sealed record PublicPage(
    PublicHeader List,
    [property: InertiaPropType(typeof(Page<PublicItem>))] InertiaProp Items) : IInertiaPage
{
    public static string Component => "Public/Show";

    public static async Task<IResult> Handle(
        string slug, PageRequest request, AppDb db, CancellationToken ct)
    {
        var list = await db.Lists.AsNoTracking()
            .Where(l => l.ShareSlug == slug)
            .Select(l => new PublicHeader(l.Title, l.Items.Count(i => !i.IsDone)))
            .FirstOrDefaultAsync(ct);
        if (list is null) return Results.NotFound();

        var items = await db.Items.AsNoTracking()
            .Where(i => i.List.ShareSlug == slug && !i.IsDone)
            .OrderBy(i => i.Id)
            .Select(i => new PublicItem(i.Id, i.Title))
            .ToPageAsync(request, ct: ct);

        // Everyone sees the same page, so the server-rendered HTML can be reused: fresh for 5 minutes, then
        // served for up to an
        // hour more while a new render is made in the background. The cache key includes the page's JSON,
        // so a changed list is
        // never served from an old render.
        return Render(new PublicPage(list, Scroll(items))).WithSsrCache(TimeSpan.FromMinutes(5), staleFor: TimeSpan.FromHours(1));
    }
}
```

Look at the last line. `.WithSsrCache(...)` is the **SSR cache**. Rendering takes time, and this page looks the same for everyone, so the finished HTML can be reused:

- For **5 minutes** the saved HTML is served without calling the SSR server at all.
- For **one hour more** it is still served, and a new render is made in the background (`staleFor`). Nobody waits.
- The cache key is built from the page's **JSON**, which includes the title and the items. If the list changes, the JSON changes, the key changes, and the old render is never used. You cannot show a stale page by mistake.

<Callout type="warning" title="Cache only pages that everyone sees the same">
A page with per-person props makes one cache entry per person. That wastes memory and gains nothing. Our list pages are **not** cached for that reason, and the public page is.
</Callout>

Turn SSR on. In `AddInertia(...)` in `Program.cs`, add:

```csharp
// Server-side rendering: Bun runs the bundle that "vite build --ssr" writes. While Vite runs in
// development, Vite renders instead.
o.Ssr.BundlePath = "ssr/ssr.js";
o.Ssr.UseNodeProcess(n => n.Executable = "bun");
```

`UseNodeProcess` makes the app start and watch the SSR process for you. If it stops answering, it is restarted, and while it is down the pages are rendered in the browser instead. Use `n.Executable = "node"` if you do not have Bun.

## 8. A reminder that appears by itself

Add a reminder time to an item. When the time comes, the **My lists** page should show it, without anyone reloading. Two parts make that work: a **worker** that notices due reminders, and a **live prop** that refreshes the page when told.

First the worker. A `BackgroundService` runs for as long as the app runs:

```csharp
using Microsoft.EntityFrameworkCore;

namespace ForgetMeNot;

// / <summary>Every 20 seconds: find reminders that are due, mark them as sent, and tell the owner's open
// pages to refresh.</summary>
public sealed class ReminderWorker(IServiceScopeFactory scopes, ILogger<ReminderWorker> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromSeconds(20));
        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            try
            {
                await SendDueRemindersAsync(stoppingToken);
            }
            catch (Exception e) when (e is not OperationCanceledException)
            {
                logger.LogError(e, "Sending reminders failed; trying again on the next tick");
            }
        }
    }

    private async Task SendDueRemindersAsync(CancellationToken ct)
    {
        using var scope = scopes.CreateScope(); // the worker lives forever, but a DbContext should not
        var db = scope.ServiceProvider.GetRequiredService<AppDb>();
        var live = scope.ServiceProvider.GetRequiredService<IInertiaLive>();
        var now = DateTime.UtcNow;

        var due = await db.Items.Include(i => i.List)
            .Where(i => i.RemindAt != null && i.RemindAt <= now && i.RemindedAt == null)
            .Take(100)
            .ToListAsync(ct);

        // saved before publishing, so a restart cannot send it twice
        foreach (var item in due) item.RemindedAt = now;
        await db.SaveChangesAsync(ct);

        foreach (var email in due.Select(i => i.List.OwnerEmail).Distinct())
        {
            await live.PublishAsync(Events.RemindersChanged(email), cancellationToken: ct);
        }

        if (due.Count > 0) logger.LogInformation("Sent {Count} reminders", due.Count);
    }
}
```

- **Every 20 seconds** is plenty for a demo. A real app might use a minute.
- **`CreateScope()`** gives the worker its own `AppDb`. The worker lives forever, but a database context must not.
- **Save first, publish second.** The reminders are marked as sent before anyone is told. If the app dies in between, nobody gets the same reminder twice.
- **`try`/`catch` around the work.** If one round fails, the worker logs it and tries again next time instead of stopping for good.

Now the line that connects the worker to the page. In `ListsPage` we wrote `.Live(Events.RemindersChanged(email))`. When the worker publishes that event, the browser reloads **only** the `reminders` prop. Nothing else on the page is touched.

Install the SignalR transport. It carries the "something changed" message to the browser:

```sh
dotnet add package Inertia.Net.Live.SignalR --version 1.9.2
bun add @microsoft/signalr
```

In `Program.cs`, register it and the worker, and map the connection endpoint:

```csharp
builder.Services.AddHostedService<ReminderWorker>();

// Live props: the server can tell a signed-in browser that something changed.
builder.Services.AddInertiaLive().AddSignalR(o =>
    o.Authorize((context, channel, ct) =>
        ValueTask.FromResult(channel.Name == $"users.{context.User?.FindFirstValue(ClaimTypes.Email)}")));

// ...after app.MapInertiaDevTools();
app.MapInertiaLiveHub(); // the SignalR connection, at /inertia-live
```

<Callout type="danger" title="This Authorize rule is the security">
Without it, nobody can join a private channel. With it, a person can join only the channel named after their own email. Without this check, anyone could listen to anyone's reminders. Keep the rule tight.
</Callout>

Finally, turn the client side on. The template already includes `ClientApp/lib/inertia-signalr.ts`. Import it in the client entry (`app.tsx` or `app.ts`) and pass it to `createInertiaApp`:

```ts
import { signalr } from './lib/inertia-signalr'

createInertiaApp({
  serverHead: true,
  live: signalr(), // props marked .Live(...) refresh themselves when the server publishes their event
})
```

Run it. Add an item with a reminder one minute from now, open **My lists** and wait. When the time comes, the reminder shows up on its own. Open the browser's network tab to see how little happens: one small request, only for `reminders`.

<Callout type="info" title="Why not just poll?">
Polling asks "anything new?" every few seconds, for every open page, all day. A live prop sends nothing until something changes, and then sends one small request. It is cheaper for the server and faster for the person.
</Callout>

<Callout type="warning" title="More than one server">
A SignalR message reaches only the browsers connected to the server that sent it, and each server would also run its own worker. Behind a load balancer, add a Redis backplane, keep the props cache in Redis (see [Redis cache](/docs/redis)), and run the worker on one instance. For a single server, what you have now is right.
</Callout>

Before the app is public, go through this short list. Each item has a reason.

| Do this | Why |
|---|---|
| Install Bun (or set `Executable = "node"`) where the app runs | The app starts the SSR bundle with it |
| Keep the Data Protection keys somewhere that survives a restart | The sign-in cookie is encrypted with them. A new key signs everyone out |
| Use EF Core migrations instead of `EnsureCreated()` | The tables will change, and `EnsureCreated()` cannot change them |
| Set `ConnectionStrings__Default` for the real database | The file next to the app is only for your laptop |
| Forward the proxy headers when you run behind one | The sign-in rate limit counts clients by address, and every client looks like the proxy. See [Deploying behind a proxy](/docs/deploying) |
| Run one instance, or add Redis for the caches and SignalR | The props cache, SSR cache and live messages are per server unless you share them |

Container examples are in [Deploying behind a proxy](/docs/deploying) and the [server-side rendering](/docs/server-side-rendering) guide. For the container's memory, use the [memory table](/docs/performance#memory-and-hosting).

        /// <summary>Where to go after signing in: the page that sent the visitor to the login page.</summary>
        public string? ReturnUrl { get; set; }

    /// <summary>One demo user (demo@example.com / password). Swap it for ASP.NET Core Identity or your user database.</summary>
    public sealed class UserStore
    {
        private readonly PasswordHasher<AuthUser> _hasher = new();
        private readonly AuthUser _demo = new("Demo User", "demo@example.com");
        private readonly string _hash;

        public UserStore() => _hash = _hasher.HashPassword(_demo, "password");

        public AuthUser? Find(string email, string password) =>
            string.Equals(email, _demo.Email, StringComparison.OrdinalIgnoreCase)
            && _hasher.VerifyHashedPassword(_demo, _hash, password) != PasswordVerificationResult.Failed
                ? _demo
                : null;
    }
