A live prop refreshes itself when the server broadcasts an event. The page response says which props listen to which events. The client subscribes to the channels of those events. When an event arrives, the client reloads the affected props or applies the values the event carries. Your components never subscribe or clean up.

Three pieces make it work:

1. **An event**, defined once as a `LiveEvent` and shared by both sides.
2. **A prop marked `.Live(event)`**, which puts its listeners in the page's `liveProps`.
3. **A publish** through `IInertiaLive`, delivered to subscribers by a transport.

<Callout type="info" title="Client version">
Live props need `@inertiajs/react`, `@inertiajs/vue3` or `@inertiajs/svelte` 3.11.0 or later. Older clients ignore `liveProps`.
</Callout>

## Define each event once

A `LiveEvent` is an event name on a `LiveChannel`. You use the same `LiveEvent` value to declare the prop and to publish the event, so the two sides always match.

```csharp
public static class OrderEvents
{
    public static LiveEvent Updated(int id) => new("OrderUpdated", LiveChannel.Private($"orders.{id}"));
    public static LiveEvent StatsChanged { get; } = new("StatsChanged", LiveChannel.Public("stats"));
}
```

A channel is `LiveChannel.Public`, `Private`, `Presence` or `EncryptedPrivate`. Channel names carry no prefix. A transport adds `private-` or `presence-` itself when its protocol needs one.

## Mark props live

```csharp
app.MapGet("/orders/{id:int}", (int id, AppDb db) => Render("Orders/Show", new InertiaProps
{
    ["order"]   = Prop(ct => db.Orders.SingleAsync(o => o.Id == id, ct))
                      .Live(OrderEvents.Updated(id))
                      .Throttle(TimeSpan.FromMilliseconds(500)),
    ["metrics"] = Defer(ct => metrics.ForOrderAsync(id, ct)).Live(OrderEvents.Updated(id)),
    ["stats"]   = Optional(() => stats.Today()).Live(OrderEvents.StatsChanged),
}));
```

The page lists every listener, including the listeners of props it left out:

```json
{
  "props": { "errors": {}, "order": { "id": 1, "status": "paid" } },
  "deferredProps": { "default": ["metrics"] },
  "liveProps": {
    "order": {
      "listeners": [
        { "channel": { "name": "orders.1", "type": "private" }, "events": ["OrderUpdated"] }
      ],
      "throttle": 500
    },
    "metrics": {
      "listeners": [
        { "channel": { "name": "orders.1", "type": "private" }, "events": ["OrderUpdated"] }
      ]
    },
    "stats": {
      "listeners": [
        { "channel": { "name": "stats", "type": "public" }, "events": ["StatsChanged"] }
      ]
    }
  }
}
```

| Call | Effect |
|---|---|
| `.Live(event)` | Adds a listener. Repeatable: call it once per event. |
| `.Live(channel, "Created", "Deleted")` | Listens to several events on one channel. |
| `Live(() => ..., event)` | The factory form of `Prop(...).Live(event)`. |
| `.Throttle(window)` | The shortest time between two reloads of the prop. The client's default is one second. |

### What combines with live

| Prop | Live? | Notes |
|---|---|---|
| `Prop`, `Always`, shared props | Yes | |
| `Defer`, `Optional` | Yes | Listeners are reported even while the value is left out. |
| `Once` | Yes | A once prop the client already holds stays subscribed. |
| `Rescue`, `Parallel` | Yes | A rescued prop stays subscribed. The next event fetches it again. |
| `Cache` | Yes | Publishing does not evict the cache. Remove the entry with `IInertiaCache` first. |
| `Merge`, `DeepMerge`, `Scroll` | No | A live prop is replaced whole, so these throw `InvalidOperationException`. Reload them from the page instead: see [Reloading scroll and merge props](#reloading-scroll-and-merge-props). |

A live prop inside an array reloads its whole array, as every [partial reload](/docs/partial-reloads) of an array descendant does. Prefer keyed objects for lists that change often.

## Shared live props

A shared live prop keeps something current on every page, such as a notification bell:

```csharp
builder.Services.AddInertia(o => o.Share("notifications", ctx =>
{
    var userId = ctx.User.FindFirstValue(ClaimTypes.NameIdentifier);
    return userId is null ? null : Prop(ct => notifications.SummaryAsync(userId, ct))
        .Live(new LiveEvent("NotificationCreated", LiveChannel.Private($"users.{userId}")));
}));
```

## Publish events

`AddInertiaLive()` registers `IInertiaLive`, the service you publish events through. A transport registers the `IInertiaLiveBroadcaster` that delivers what `IInertiaLive` publishes.

```csharp
builder.Services.AddInertiaLive();   // then a transport: .AddSignalR() or your own IInertiaLiveBroadcaster
```

<Tabs>
<Tab label="Reload">

```csharp
// Everyone else on the channel reloads `order`; the caller already has the response.
app.MapPost("/orders/{id:int}/ship", async (int id, HttpContext context, IInertiaLive live) =>
{
    await orders.ShipAsync(id);
    await live.PublishAsync(OrderEvents.Updated(id), exceptSocketId: context.InertiaRequest().SocketId);
    return Back();
});
```

</Tab>
<Tab label="With values">

```csharp
// Clients apply the value without a request; live props left out are reloaded.
await live.PublishAsync(OrderEvents.Updated(order.Id), new { order = OrderDto.From(order) });
```

</Tab>
<Tab label="Explicit metadata">

```csharp
// Written with that context's own options, as JsonSerializer would.
await live.PublishAsync(OrderEvents.Updated(order.Id), new OrderProps(dto), AppJsonContext.Default.OrderProps);
```

</Tab>
</Tabs>

- **Without values**, every client reloads the live props that listen to the event, each with its own request and its own data.
- **With values**, the props named in the values are updated in place. The values are keyed by prop path (`"auth.user"` stays a flat key). Values use the page serializer options, so they match what a reload returns. Under Native AOT, the type needs to be in your registered JSON context, like any prop type.
- **`exceptSocketId`** leaves one connection out, usually the client that made the change. The client sends its id as `X-Socket-Id`, and `HttpContext.InertiaRequest().SocketId` reads it. The client supplies the header, so it is only ever used to exclude a connection.

<Callout type="danger" title="Every subscriber sees the same values">
A broadcast reaches every client on the channel. Only publish values that everyone allowed on the channel may see. When a value depends on the user, publish without values and let each client reload its own data.
</Callout>

A broadcaster delivers this payload:

```json
{
  "__inertia": {
    "event": "OrderUpdated",
    "props": { "order": { "id": 1, "status": "shipped" } }
  }
}
```

## Resolve values for a broadcast

Use plain values with `IInertiaLive.PublishAsync` when you already have the data. If you have prop definitions instead,
resolve them first. This handler fragment assumes `http`, `orders`, `id`, `live`, `orderUpdated` and `ct` are in scope:

```csharp
var values = await BroadcastPropsAsync(http, new InertiaProps
{
    ["order"] = Prop(ct => orders.FindAsync(id, ct)),
    ["stats.total"] = Defer(() => 42),
});
await live.PublishAsync(orderUpdated, values, exceptSocketId: http.InertiaRequest().SocketId, cancellationToken: ct);
```

Visit filters do not restrict a broadcast. Optional, deferred and once values all resolve. A rescued value is left out.
Dot-path keys stay flat. No page or DevTools entry is created.
Only publish values that every subscriber of the channel is allowed to see.

## On the client

Read a live prop like any other prop. `useProp` exposes the prop's loading state. The `live` router event is cancelable, so a listener can hold an update back, for example to show a "new posts" button instead:

<Tabs>
  <Tab label="React">

```tsx
import { router, useProp } from '@inertiajs/react'
import { useEffect, useState } from 'react'

type Order = { id: number; status: string }

export default function Show() {
  const order = useProp<Order>('order')   // { value, loading, loaded }
  const [newPosts, setNewPosts] = useState(false)

  // Returning false holds the update back.
  useEffect(
    () =>
      router.on('live', (event) => {
        if (event.detail.props.includes('posts')) {
          setNewPosts(true)
          return false
        }
      }),
    [],
  )

  return (
    <>
      <p>Status: {order.value?.status}{order.loading && ' (updating...)'}</p>
      {newPosts && <button onClick={() => router.reload({ only: ['posts'] })}>New posts</button>}
    </>
  )
}
```

  </Tab>
  <Tab label="Vue">

## SignalR

`Inertia.Net.Live.SignalR` runs the transport inside your app. It provides:

- a SignalR hub the browser subscribes to
- channel authorization
- the broadcaster that `IInertiaLive` publishes through

```sh
dotnet add package Inertia.Net.Live.SignalR
npm install @microsoft/signalr # or: bun add, pnpm add, yarn add @microsoft/signalr
```

```csharp
builder.Services.AddInertiaLive().AddSignalR(o =>
    o.Authorize((context, channel, ct) =>
        ValueTask.FromResult(channel.Name == $"users.{context.UserIdentifier}")));

var app = builder.Build();
app.UseAuthentication();
app.UseAuthorization();
app.UseInertia();
app.MapInertiaLiveHub();   // /inertia-live
```

Apps created with `dotnet new inertia` ship the client transport as `ClientApp/lib/inertia-signalr.ts`. In other apps, copy [the file](https://github.com/adzamkomladev/Inertia.Net/blob/main/src/Inertia.Net.Templates/content/common/ClientApp/lib/inertia-signalr.ts) into your app. Then turn the transport on:

```ts
import { signalr } from './lib/inertia-signalr'

createInertiaApp({ live: signalr() })
```

`@microsoft/signalr` loads on the first subscription, so pages without live props never download it. When a dropped connection comes back, the transport joins its channels again. Inertia then reloads every live prop once, which catches up on missed events.

### Who may join a channel

| Channel | Who joins |
|---|---|
| `Public` | Anyone who reaches the hub. Set `o.AuthorizePublicChannels = true` to ask the authorizer too. |
| `Private`, `Presence`, `EncryptedPrivate` | Only connections the authorizer allows. With no authorizer, nobody joins. |

For rules that need services, implement `ILiveChannelAuthorizer` and register it with `o.Authorize<OrderChannelAuthorizer>()`. The authorizer is created for each subscription, with constructor injection. SignalR has no presence member lists or end-to-end encryption, so presence and encrypted-private channels are authorized like private ones.

The hub answers requests from other origins with 403. Add trusted origins to `o.AllowedOrigins`. The origin check takes the place of antiforgery tokens on the hub. Connections close when their authentication expires.

<Callout type="info" title="More than one server">
SignalR groups exist on one server only. When you run several instances, or publish from a worker, add an Inertia backplane on the Redis or PostgreSQL you already run: `AddSignalR().AddRedisBackplane(...)` or `.AddPostgresBackplane(...)`. See [Live props at scale](/docs/live-props-at-scale). Do not also register SignalR's own Redis backplane or Azure SignalR for the same hub: every event would arrive twice, so startup fails to tell you.
</Callout>

The [package README](https://github.com/adzamkomladev/Inertia.Net/blob/main/src/Inertia.Net.Live.SignalR/README.md) lists the client options, how channels map to SignalR groups, and the security notes.

## Server-Sent Events

`Inertia.Net.Live.Sse` delivers live props over one `text/event-stream` endpoint. The browser reads it with its built-in `EventSource`, so there is no client library to install.

```sh
dotnet add package Inertia.Net.Live.Sse
```

```csharp
builder.Services.AddInertiaLive().AddSse(o =>
    o.Authorize((context, channel, ct) =>
        ValueTask.FromResult(channel.Name == $"users.{context.UserIdentifier}")));

var app = builder.Build();
app.UseAuthentication();
app.UseAuthorization();
app.UseInertia();
app.MapInertiaLiveSse();   // /inertia-live
```

Apps created with `dotnet new inertia` ship the client transport as `ClientApp/lib/inertia-sse.ts`. In other apps, copy [the file](https://github.com/adzamkomladev/Inertia.Net/blob/main/src/Inertia.Net.Templates/content/common/ClientApp/lib/inertia-sse.ts) into your app:

```ts
import { sse } from './lib/inertia-sse'

createInertiaApp({ live: sse() })
```

The channel rules and the `ILiveChannelAuthorizer` are the same as for SignalR. One authorizer class serves both transports, and its `HubCallerContext` wraps the stream request. The channels are part of the stream URL, so the stream reopens when a page joins or leaves a channel. These cases are handled for you:

- A stream from another origin gets a 403.
- A stream ends when its sign-in expires. The client reconnects, and its channels are authorized again.
- A client too slow to keep up is disconnected. It reloads its live props when it reconnects.

<Callout type="info" title="One instance, or any number with a backplane">
Without a backplane, a publish reaches only the clients connected to the instance that sent it. With several instances, or a separate worker, add `.AddRedisBackplane(...)` or `.AddPostgresBackplane(...)` and every instance delivers every event. SSE needs no sticky sessions. See [Live props at scale](/docs/live-props-at-scale).
</Callout>

The [package README](https://github.com/adzamkomladev/Inertia.Net/blob/main/src/Inertia.Net.Live.Sse/README.md) lists the options and the wire format.

## Choose a transport

| | SSE | SSE + backplane | SignalR | SignalR + backplane | Polling |
|---|---|---|---|---|---|
| Client library | none | none | `@microsoft/signalr` | `@microsoft/signalr` | none |
| Several web instances | no | yes | no | yes | yes |
| Publish from another process | no | yes | no | yes | n/a |
| Publish on commit | no | with PostgreSQL | no | with PostgreSQL | n/a |
| Extra infrastructure | none | Redis, or the PostgreSQL you run | none | Redis, or the PostgreSQL you run | none |
| Client-to-server messages | no | no | yes | yes | n/a |
| Latency | push | push | push | push | up to the interval |

Packages on NuGet: [Inertia.Net.Live.Sse](https://www.nuget.org/packages/Inertia.Net.Live.Sse), [Inertia.Net.Live.SignalR](https://www.nuget.org/packages/Inertia.Net.Live.SignalR), [Inertia.Net.Redis](https://www.nuget.org/packages/Inertia.Net.Redis) and [Inertia.Net.Postgres](https://www.nuget.org/packages/Inertia.Net.Postgres) for the backplanes.

## Notify after commit

With the PostgreSQL backplane, publish inside your database transaction: the event goes out only if the transaction commits.

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);
order.Status = OrderStatus.Shipped;
await db.SaveChangesAsync(ct);
await postgres.PublishAsync(live.CreateMessage(OrderEvents.Updated(order.Id)), db.Database.GetDbConnection(), tx.GetDbTransaction(), ct);
await tx.CommitAsync(ct);   // delivered now
```

If anything throws before `CommitAsync`, the transaction rolls back and no client hears about a change that never happened:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);
await postgres.PublishAsync(live.CreateMessage(OrderEvents.Updated(order.Id)), db.Database.GetDbConnection(), tx.GetDbTransaction(), ct);
await tx.RollbackAsync(ct); // nothing is delivered, to any instance
```

`postgres` is the `PostgresLiveBackplane` that `AddPostgresBackplane()` registers; inject it like any service. See [Publish on commit](/docs/live-props-at-scale#publish-on-commit) for the details.

## Reloading scroll and merge props

A `Scroll(...)` or `Merge(...)` prop cannot be live, because a live reload would merge the reloaded page into the list. Reload such a prop from the page instead, with `ClientApp/lib/inertia-live-reload.ts`, which `dotnet new inertia` apps include:

```csharp
o.TypeScript.RoutesOutputPath = "ClientApp/types/routes.ts";
o.TypeScript.LiveEvents(Events.PostCreated);   // exported from routes.ts as liveEvents.PostCreated
```

`liveReload` works like this:

- Events within `debounce` milliseconds become one reload. The default is 250.
- A reload waits for a visit that is in progress.
- The scroll position is kept.
- The client that caused the event (`exceptSocketId`) is not reloaded.

`reset` replaces the prop instead of merging it, so the reload brings no duplicates. The SignalR and Server-Sent Events client transports deliver a channel's events to every subscriber. See [Typed routes](/docs/typed-routes) for `routes.ts`.

## Custom transports and backplanes

To scale a transport of your own across instances, implement `IInertiaLiveLocalTransport` (deliver to this instance's clients, and resync them after a gap) instead of `IInertiaLiveBroadcaster`; any backplane then carries its events. To use another store as the backplane, implement `IInertiaLiveBackplane`: it only moves the bytes Inertia.Net writes (`LiveWire`), and reports a gap with `missed`. See [docs/protocol.md](https://github.com/adzamkomladev/Inertia.Net/blob/main/docs/protocol.md#live-backplane-wire-format) for the wire format.

The page metadata and the payload do not depend on SignalR, so any transport works:

- **Pusher-protocol servers** (Reverb, Soketi, Ably, Pusher) work with the client's built-in `pusher()` or `echo()` transport. On the server, implement `IInertiaLiveBroadcaster` with your server's publish API.
- **Anything else** (Action Cable, Azure Web PubSub): implement `IInertiaLiveBroadcaster` on the server and a `LiveTransport` on the client.

A broadcaster has one method. It receives the channel, the finished payload and the connection to skip:

```csharp
public sealed class MyBroadcaster : IInertiaLiveBroadcaster
{
    public ValueTask PublishAsync(LiveMessage message, CancellationToken cancellationToken = default)
    {
        // message.Channel.Key:      "private:orders.1"
        // message.Payload:          {"__inertia":{"event":"OrderUpdated",...}}, a JsonElement
        // message.ExceptSocketId:   the connection to leave out, or null
        throw new NotImplementedException("Send message.Payload to the channel's subscribers.");
    }
}
```

`InertiaPage.LiveProps` holds the live metadata, and `HasLive` asserts it. Write the channel as `"{type}:{name}"`:

```csharp
await response.AssertInertiaAsync(page => page

```

## Limits, proxies and authorization changes

SignalR defaults to 64 subscriptions per connection and a 200-character channel name. Configure `MaxSubscriptionsPerConnection` and `MaxChannelNameLength` through the SignalR options. Both must be positive. Behind a TLS-terminating proxy, configure trusted forwarded headers once and run `UseForwardedHeaders()` before the hub. The origin and scheme checks then see the external address.

Authorization is checked when a client subscribes, not continuously. If access changes, disconnect the client, or use a transport or application strategy that enforces revocation. A `removed` event can tell the UI to update, but it is not a security mechanism for revoking access.
