How does an Inertia.Net app compare with the same app built in other full-stack frameworks? `benchmarks/frameworks` builds one small todo app six ways, runs each in Docker and loads it with the same client. Each app is written the way a team in that framework usually writes it.

| App | Data access | Dashboard cache | Form validation |
|---|---|---|---|
| Inertia.Net, JIT | EF Core | `InertiaProp.Cache` on Redis | `AddValidation()` and `WithInertiaValidation()` |
| Inertia.Net, Native AOT | Npgsql | `InertiaProp.Cache` on Redis | `AddValidation()` and `WithInertiaValidation()` |
| Next.js | Drizzle | `'use cache: remote'` with a Redis handler | zod |
| TanStack Start | Drizzle | Nitro's `defineCachedFunction` on Redis | zod |
| Nuxt | Drizzle | Nitro's `defineCachedFunction` on Redis | zod |
| Laravel (Octane, FrankenPHP) | Eloquent | `Cache::remember` on Redis | Form Request |

The Native AOT build uses Npgsql because EF Core is not yet trim- or AOT-safe. The [Native AOT](/docs/native-aot) page explains the options.

Every app serves the same routes: a home page, a paged todo list, a cached dashboard, a CPU-heavy route and a new-todo form. Each runs in SSR and SPA mode with TypeScript. Nuxt renders Vue pages; the others render the same React pages. The app code, the run script and every setting are in [benchmarks/frameworks](https://github.com/adzamkomladev/Inertia.Net/tree/main/benchmarks/frameworks).

## Results

From one run on GitHub-hosted runners on 2026-11-16. Each route ran on its own 4-vCPU runner with all six apps on it, so every row compares apps on the same machine. Each app was limited to 2 CPUs and 2 GB, under 16 keep-alive connections. Every request succeeded, and every SSR response was really server-rendered.

**Memory and startup**

| App | Memory at rest, SPA / SSR | Cold start, SPA / SSR | Image, SPA / SSR |
|---|---:|---:|---:|
| Inertia.Net, Native AOT | **17** / 46 MB | **216** / 514 ms | **34** / 98 MB |
| Inertia.Net, JIT | 27 / 60 MB | 522 / 1,108 ms | 125 / 189 MB |
| TanStack Start | 28 / 29 MB | 263 / **258** ms | 166 MB |
| Next.js | 72 / 76 MB | 715 / 775 ms | 185 MB |
| Nuxt | 138 / 139 MB | 340 / 739 ms | 169 MB |
| Laravel | 98 / 154 MB | 785 / 951 ms | 252 / 311 MB |

Memory is the whole container: for SSR it includes the Node renderer, and for Laravel all its PHP workers.

## What the numbers say

- **Inertia.Net served the most requests on every route.** The Native AOT build served 3 times as many SSR first visits as TanStack Start, 5 times as many as Nuxt, and 11 to 12 times as many as Next.js and Laravel.
- **The data layer matters more than JIT or AOT.** On database routes the Native AOT build, using Npgsql, served 59% more navigations and twice the SSR first visits of the JIT build using EF Core. On the CPU-heavy route, which doesn't touch the database, the JIT build was about 17% faster.
- **Saving a row is limited by the database for every app.** Valid posts are close across the fastest apps. Invalid posts, which write nothing, show the framework's own cost: Inertia.Net handled 16,000 to 18,000 per second, including validation, the antiforgery check and the redirect.
- **The Inertia apps check for forged requests on every page.** Inertia.Net checks an antiforgery token and Laravel checks a session. The Node apps' API routes do neither by default.
- **CPU-heavy work is mostly a language-speed test.** A Node process runs one request's JavaScript at a time, so the plain `/compute` route stays near 200 to 240 requests per second however many CPUs it has. .NET spreads work over every core without extra code.

These numbers come from one run on shared cloud machines, with the load client on the same machine as the apps. Measure your own app before you rely on them. Every route in both modes, the latency percentiles and the fixed-rate runs are in the [full results](https://github.com/adzamkomladev/Inertia.Net/blob/main/benchmarks/frameworks/results/2026-11-16-v3.md). The [README](https://github.com/adzamkomladev/Inertia.Net/tree/main/benchmarks/frameworks) lists the caveats and how to run the comparison yourself.

For the cost of Inertia.Net next to a plain Minimal API, see [Performance](/docs/performance).
