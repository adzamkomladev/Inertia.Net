How does an Inertia.Net app compare with the same app built in other full-stack frameworks? `benchmarks/frameworks` builds one small todo app five ways, runs each in Docker and loads it with the same client. Each app is written the way a team in that framework usually writes it.

| App | Data access | Dashboard cache | Form validation |
|---|---|---|---|
| Inertia.Net, JIT | EF Core | `InertiaProp.Cache` on Redis | `AddValidation()` and `WithInertiaValidation()` |
| Inertia.Net, Native AOT | Npgsql | `InertiaProp.Cache` on Redis | `AddValidation()` and `WithInertiaValidation()` |
| Next.js | Drizzle | `'use cache: remote'` with a Redis handler | zod |
| TanStack Start | Drizzle | Redis | zod |
| Laravel (Octane, FrankenPHP) | Eloquent | `Cache::remember` on Redis | Form Request |

The Native AOT build uses Npgsql because EF Core is not yet trim- or AOT-safe. The [Native AOT](/docs/native-aot) page explains the options.

Every app serves the same routes: a home page, a paged todo list, a cached dashboard, a CPU-heavy route and a new-todo form. Each runs in SSR and SPA mode, with React and TypeScript on the client. The app code, the run script and every setting are in [benchmarks/frameworks](https://github.com/adzamkomladev/Inertia.Net/tree/main/benchmarks/frameworks).

## Results

From one run on a GitHub-hosted runner (4 vCPUs, AMD EPYC 7763) on 2026-11-16. Each app was limited to 2 CPUs and 2 GB, under 16 keep-alive connections. Every request succeeded, and every SSR response was really server-rendered.

**Memory and startup**

| App | Memory at rest, SPA / SSR | Cold start, SPA / SSR | Image, SPA / SSR |
|---|---:|---:|---:|
| Inertia.Net, Native AOT | **20** / 50 MB | **239** / 704 ms | **34** / 98 MB |
| Inertia.Net, JIT | 58 / 91 MB | 743 / 1,297 ms | 125 / 189 MB |
| TanStack Start | 86 / 93 MB | 473 / 475 ms | 167 MB |
| Next.js | 132 / 138 MB | 1,141 / 1,237 ms | 185 MB |
| Laravel | 105 / 161 MB | 1,212 / 1,374 ms | 252 / 311 MB |

Memory is the whole container: for SSR it includes the Node renderer, and for Laravel all its PHP workers.

**Requests per second** (SSR mode; higher is better)

| Route | Inertia.Net JIT | Inertia.Net AOT | TanStack Start | Next.js | Laravel |
|---|---:|---:|---:|---:|---:|
| `/todos?perPage=25`, first visit | 1,836 | **2,449** | 934 | 254 | 192 |
| `/todos?perPage=25`, client-side navigation | 3,439 | **5,037** | 1,973 | 1,075 | 301 |
| `/dashboard`, client-side navigation | 6,935 | **8,708** | 5,874 | 1,447 | 739 |
| New todo, valid post | 3,482 | **4,887** | 2,419 | 1,117 | 447 |
| New todo, invalid post | 6,468 | **8,298** | 3,806 | 1,503 | 452 |
| `/compute?n=20000`, CPU-heavy | **986** | 711 | 164 | 145 | 50 |

## What the numbers say

- **Inertia.Net served the most requests on every route and used the least memory.** With SSR it served 2 to 2.6 times as many first visits as TanStack Start, and 7 to 13 times as many as Next.js and Laravel.
- **The data layer matters more than JIT or AOT.** On database routes the Native AOT build, using Npgsql, served about 45% more navigations and 40% more form posts than the JIT build using EF Core. On the CPU-heavy route, which doesn't touch the database, the JIT build was about 40% faster.
- **The Inertia apps check for forged requests on every page.** Inertia.Net checks an antiforgery token and Laravel checks a session. The Node apps' route handlers do neither by default.
- **CPU-heavy work is mostly a language-speed test.** A Node process runs one request's JavaScript at a time, so the plain `/compute` route stays near 150 requests per second however many CPUs it has. .NET spreads work over every core without extra code.

These numbers come from one run on a shared cloud machine, with the load client on the same machine. Measure your own app before you rely on them. Every route, the latency percentiles and the fixed-rate runs are in the [full results](https://github.com/adzamkomladev/Inertia.Net/blob/main/benchmarks/frameworks/results/2026-11-16-v2.md). The [README](https://github.com/adzamkomladev/Inertia.Net/tree/main/benchmarks/frameworks) lists the caveats and how to run the comparison yourself.

For the cost of Inertia.Net next to a plain Minimal API, see [Performance](/docs/performance).
