Choosing a full-stack framework is mostly about how you like to build. Speed and cost still matter, though, and they are hard to compare from each project's own claims. So we built the same small app in five frameworks, wrote each one the way that framework's own teams would, and measured them side by side.

This page explains what was built, introduces each framework and what it is good at, and then walks through the results in plain terms.

## The short version

- **Inertia.Net handled the most traffic in every test**, from first page loads to form posts to heavy calculations. Its Native AOT build also used the least memory and started fastest.
- **TanStack Start is the leanest JavaScript option.** It used as little memory as Inertia.Net's normal build and started the fastest of all the server-rendered apps.
- **Nuxt's API is very quick**, but its server-rendered pages were slower than the other JavaScript frameworks except Next.js.
- **Next.js and Laravel served the fewest requests** in this setup. Both still answered in a few milliseconds at everyday traffic levels.
- **With every framework's own caching turned on, Inertia.Net was still the fastest**, by 2 to 6 times over the next best on cached first visits.
- **At normal traffic every framework is fast enough.** The differences matter when traffic spikes, when you pay per server, or when a page does heavy work.

## What we built

Each framework runs the same todo app on the same Postgres database and Redis cache:

- **Home page**: a short list of features.
- **Todo list**: 25 or 100 todos from a table of 10,000, newest first.
- **Dashboard**: totals for the whole table, cached in Redis for 60 seconds.
- **New todo form**: checks four fields and saves the todo, or shows one error per field.
- **Heavy page**: a CPU-intensive calculation, run once on one core and once split across all cores.

Each app runs in two modes. In **SSR mode** the server sends a fully rendered page on the first visit. In **SPA mode** the server sends an empty shell and the browser renders it. After the first visit, moving between pages only fetches data, in every framework.

Before any measuring, a parity check confirms that every app returns exactly the same todos, totals, calculation results and error messages. If one app did less work, it would show up there.

## The frameworks

<Contenders names={['Inertia.Net', 'Next.js', 'TanStack Start', 'Nuxt', 'Laravel']} />

### Inertia.Net

Inertia.Net lets you write the server in ASP.NET Core and the pages in React, Vue or Svelte, without building a separate API. Controllers or Minimal API handlers return a page name and its data; Inertia's client does the routing in the browser.

**How it was built here**: a Minimal API with React pages, EF Core for the database, `InertiaProp.Cache` for the dashboard, .NET validation with `WithInertiaValidation()`, and antiforgery protection on every form. It ran in two builds:

- **JIT**: the normal .NET build, which optimises itself while it runs.
- **Native AOT**: compiled ahead of time into one small executable. EF Core doesn't support Native AOT yet, so this build reads the database with Npgsql directly. See [Native AOT](/docs/native-aot).

**Strengths**: .NET's speed and its use of every CPU core, a mature type-safe backend (EF Core, Identity, validation, background jobs), small Native AOT images, and a frontend that is still plain React, Vue or Svelte.

### Next.js

Next.js is the most widely used React framework. Its App Router mixes server and client components, and it has its own caching, routing, image handling and a large ecosystem around it.

**How it was built here**: the App Router with server components, Drizzle for the database, zod for validation, and the dashboard cached with `'use cache: remote'` and a Redis cache handler. The form posts to a route handler.

**Strengths**: the biggest React ecosystem and community, React Server Components, static generation and incremental regeneration for content sites, and first-class hosting on Vercel and other platforms.

### TanStack Start

TanStack Start is a newer full-stack React framework built on TanStack Router. It focuses on type-safe routes, type-safe server functions and explicit data loading, and runs on Vite with Nitro as its server.

**How it was built here**: file-based routes with loaders and server functions, Drizzle, zod, and the dashboard cached with Nitro's `defineCachedFunction` stored in Redis.

**Strengths**: end-to-end type safety from route parameters to server calls, a light runtime, very fast startup, and Vite's fast developer experience. It is still young, and its Node server uses Nitro 3, which is a release candidate.

### Nuxt

Nuxt is the main full-stack framework for Vue. It brings file-based pages, auto-imports, data fetching with `useFetch`, and a server layer for APIs, all on Nitro.

**How it was built here**: Vue pages that fetch their data with `useFetch`, API routes on Nitro, Drizzle, zod, and the same Nitro cache in Redis as TanStack Start. Nuxt renders Vue, while the other apps render the same React pages, so part of any difference in page rendering comes from Vue, not Nuxt itself.

**Strengths**: the most complete Vue experience, conventions that remove a lot of setup, a big module ecosystem, and a fast API layer that can be deployed almost anywhere.

### Laravel

Laravel is PHP's most popular framework. With Inertia, its controllers return React, Vue or Svelte pages the same way Inertia.Net does. Here it runs on Octane with FrankenPHP, which keeps the app in memory between requests instead of starting fresh each time.

**How it was built here**: Eloquent models, a Form Request for validation, `Cache::remember` for the dashboard, and CSRF protection with cookie sessions.

**Strengths**: a famously productive developer experience, everything built in (auth, queues, mail, scheduling, storage), a huge ecosystem, and the official Inertia adapter that started it all.

## The results

All six apps ran on GitHub's cloud machines. Each test route got its own machine with every app on it, so the apps in any one row of the tables below shared the same hardware. Each app was limited to 2 CPU cores and 2 GB of memory. Every request succeeded, and every server-rendered page really was rendered on the server.

### Memory, startup and image size

Less memory means more apps per server and a smaller hosting bill. Faster startup helps when scaling up under load or running on platforms that start apps on demand.

| App | Memory when idle, SPA / SSR | Startup time, SPA / SSR | Docker image, SPA / SSR |
|---|---:|---:|---:|
| Inertia.Net, Native AOT | **17** / 46 MB | **216** / 514 ms | **34** / 98 MB |
| Inertia.Net, JIT | 27 / 60 MB | 522 / 1,108 ms | 125 / 189 MB |
| TanStack Start | 28 / 29 MB | 263 / **258** ms | 166 MB |
| Next.js | 72 / 76 MB | 715 / 775 ms | 185 MB |
| Nuxt | 138 / 139 MB | 340 / 739 ms | 169 MB |
| Laravel | 98 / 154 MB | 785 / 951 ms | 252 / 311 MB |

In SSR mode the Inertia apps also run a small Node.js process to render pages, which is why their SSR memory is higher. For Laravel the figure includes all its PHP workers.

## Inertia.Net with its caching turned on

All the results above run every framework without page caching, so they compare the frameworks themselves. A real app usually caches what it can. So we ran Inertia.Net once more, next to itself, with its own caching features turned on:

- **The SSR render cache** keeps the HTML of a server-rendered page. When the next visitor gets exactly the same page, Inertia.Net sends that HTML without asking Node to render it again. See [Server-side rendering](/docs/server-side-rendering).
- **Two Node renderers** instead of one, so rendering can use both CPU cores.
- **Cached props with stale-while-revalidate**: the dashboard totals and each page of the todo list are kept in memory for a few seconds and refreshed in the background. See [Props](/docs/props).

Plain and tuned builds ran side by side on the same machines:

| Page, first visit | JIT | JIT, tuned | Native AOT | Native AOT, tuned |
|---|---:|---:|---:|---:|
| Home | 3,528 | **20,800** | 4,378 | 17,952 |
| Todo list, 25 rows | 1,561 | **25,756** | 3,293 | 23,443 |
| Todo list, 100 rows | 562 | **15,119** | 1,033 | 13,745 |
| Dashboard | 2,819 | **20,903** | 3,586 | 18,054 |
| New todo form | 7,068 | **56,746** | 7,773 | 49,923 |

With caching on, server-rendered pages were served 4 to 27 times faster, in about a millisecond, because a cached page skips rendering entirely. Form posts and the heavy calculation didn't change, since nothing there is cached. The second Node renderer adds about 25 MB of memory.

<Callout type="warning" title="Cache what everyone sees the same way">
The render cache is keyed by the page's data, so pages with per-user data make one entry per user. Turn it on for pages that are the same for every visitor, such as landing, catalog and article pages. The other frameworks have caching of their own, so these numbers aren't in the tables above; the next section turns caching on for all of them.
</Callout>

## Every framework with its caching turned on

Comparing a cached Inertia.Net with uncached rivals wouldn't be fair, so we gave every app its own framework's caching, set the same way: pages kept for 60 seconds and todo lists for 10, each served stale while a fresh copy is made in the background, all kept in the app's memory.

- **Next.js:** `'use cache'` on the page components and their data.
- **TanStack Start and Nuxt:** Nitro route rules, which store the whole response.
- **Laravel:** the popular [spatie/laravel-responsecache](https://github.com/spatie/laravel-responsecache) package, which also stores the whole response.

Requests per second for a first visit, every app with caching on:

| Page, first visit | Inertia.Net | Inertia.Net (AOT) | Nuxt | TanStack Start | Laravel | Next.js |
|---|---:|---:|---:|---:|---:|---:|
| Home | **55,711** | 50,970 | 18,471 | 12,997 | 1,177 | 558 |
| Todo list, 25 rows | **34,020** | 32,889 | 15,481 | 9,543 | 1,201 | 439 |
| Todo list, 100 rows | **22,834** | 20,007 | 6,835 | 3,882 | 868 | 201 |
| Dashboard | **55,439** | 50,105 | 18,151 | 11,680 | 1,206 | 424 |
| New todo form | **57,611** | 51,266 | 18,603 | 12,129 | 1,180 | 504 |

- **Inertia.Net served 2 to 3 times more than Nuxt and 3 to 6 times more than TanStack Start**, the next fastest. It did so while still running your code and loading fresh page data on every request, which the Nuxt, TanStack Start and Laravel caches skip.
- **Nuxt and TanStack Start gained the most from caching** among the JavaScript frameworks, up to 15 times for Nuxt.
- **Laravel got 2 to 5 times faster** but stopped near 1,200 requests per second, because every request still goes through its session and security layers.
- **Next.js didn't get faster.** Its cache stores the output of components, but a page that reads the address bar, like the todo list, is still turned into HTML on every request. Next.js only serves ready-made HTML for pages that never change per request.

## What Inertia.Net caches, and what it doesn't

Inertia.Net has two caches that work together, and you choose what goes in each.

**The SSR render cache stores HTML, not data.** On a first visit Inertia.Net still runs your endpoint and builds the page's data as usual. It then looks up that exact data: if the same page with the same data was rendered recently, it sends the stored HTML and Node isn't called at all. Rendering with Node is the most expensive step of a server-rendered page, so this is where most of the speed comes from. Because the lookup uses the data itself, the cache can never show an out-of-date page: when one todo changes, the data changes, and the page is rendered fresh.

**Cached props store data.** Add `.Cache(key, duration)` to a prop and its value is kept, in memory or in Redis, so the database isn't asked again until it expires. With `staleFor`, an expired value is still served while a fresh one loads in the background. This is the only place Inertia.Net will show data that is a little old, and only for the props you mark.

In the benchmark's tuned app, a todo list visit therefore reads the rows from the prop cache, finds the HTML in the render cache, and sends it, all in well under a millisecond on the server. Moving between pages in the browser fetches only data and never involves Node, so there the prop cache does the work.

This is different from the other frameworks' caches, which store the whole response under its address. Those skip your code entirely on a hit, but they show the same response, possibly out of date, until it expires, and they need care so that one user's page isn't served to another. Inertia.Net always runs your code, so permissions and per-user data are checked on every request, and you decide which data may be a little old.

See [Server-side rendering](/docs/server-side-rendering) for the render cache and [Props](/docs/props) for cached props.

## What this means for you

- **Pick the framework your team enjoys and knows.** All five are fast enough for most apps at normal traffic.
- **Choose Inertia.Net** if you want a .NET backend with a React, Vue or Svelte frontend, if you care about hosting cost and headroom under load, or if your pages do real work on the server.
- **Choose Native AOT** for the smallest memory, image and startup time, if plain Npgsql or Dapper-style data access suits you.
- **Choose TanStack Start** for a light, type-safe React stack in TypeScript end to end.
- **Choose Next.js** for the largest React ecosystem, static and incrementally generated content, or Vercel's platform.
- **Choose Nuxt** if your team writes Vue and wants batteries-included conventions.
- **Choose Laravel** for PHP's most productive ecosystem and everything built in.

<Callout type="info" title="How to read these numbers">
These come from one run on shared cloud machines, with the load generator running next to the apps. Different routes ran on different machines, so compare apps within a table, not one table with another. Measure your own app on your own hardware before you rely on any of them.
</Callout>
