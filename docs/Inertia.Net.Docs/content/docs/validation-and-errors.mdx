Inertia forms post, expect a redirect, and read validation errors from `props.errors` on the next page. Inertia.Net performs the redirect and carries the errors across it.

- A field maps to its **first** message. With `o.WithAllErrors = true` it maps to an array of all messages (the client's `form.withAllErrors()` expects that).
- Error keys use dotted indices, for example `items.0.email`. Names use JSON member aliases when metadata exposes them and the applicable naming policy for other members. Dictionary keys are preserved. Minimal API and MVC use the page serializer’s HTTP JSON options; FastEndpoints uses its binding serializer policy. Custom resolvers that omit member metadata and paths without a model schema may fall back to naming-policy conversion; align field names and serializer settings.
- **Error bags.** The client sends `X-Inertia-Error-Bag: createUser` when the form has `errorBag="createUser"`. Errors arrive as `errors: { createUser: { email: "..." } }`. Without the header, `errors` is the flat object `{ email: "..." }`. A bag stored under a name other than `default` is always nested by bag name.

```ts
router.post('/users', data, { errorBag: 'createUser' })
```

## Validation libraries

| Backend | Validation |
|---|---|
| Minimal API | .NET 10 source-generated DataAnnotations through `AddValidation()`; `ValidationProblem` results; call FluentValidation `IValidator<T>` manually and return `WithErrors` |
| MVC | MVC model validation and `ModelState` |
| FastEndpoints | FastEndpoints validators, including FluentValidation |

## Minimal API

`WithInertiaValidation()` applies to a route or route group and requires `services.AddValidation()`. Without validation resolvers, it throws `InvalidOperationException` when the endpoint is constructed. Routing may construct endpoints lazily, so this need not happen during application startup.

```csharp
builder.Services.AddValidation();

app.MapPost("/users", (CreateUserInput input, AppDb db) =>
{
    db.Add(input);
    return Results.Redirect("/users");
}).WithInertiaValidation();

app.MapGroup("/admin").WithInertiaValidation()
   .MapPost("/roles", (RoleInput input) => Results.Redirect("/admin/roles"));
```

For an Inertia request that is not a GET, a failure becomes a redirect back (303 for PUT/PATCH/DELETE) with the errors. Every other client still gets the normal `400` validation problem. A handler that returns `TypedResults.ValidationProblem(...)`, `Results.ValidationProblem(...)` or an `HttpValidationProblemDetails` is converted the same way.

On .NET 11, async validators (`AsyncValidationAttribute`, `IAsyncValidatableObject`) report through `WithInertiaValidation()` and `WithInertiaPrecognition()` like synchronous attributes. A body that cannot be bound (malformed JSON) is still a `400` on both .NET 10 and .NET 11, never a redirect back without errors or a Precognition success.

<Callout type="warning" title="Why not rely on AddValidation alone?">
The built-in .NET 10 validation filter is added automatically and always runs outermost: it writes the 400 itself before any filter you add can see it. `WithInertiaValidation()` disables it on the endpoint and runs the same source-generated validation itself. Do not combine it with your own `.DisableValidation()`.
</Callout>

To report errors yourself, without attribute validation:

```csharp
app.MapPost("/login", (LoginInput input, SignInService auth) =>
    auth.TryLogin(input)
        ? Results.Redirect("/")
        : Back().WithErrors(new Dictionary<string, string>
        {
            ["email"] = "These credentials do not match.",
        }));
```

`Back().WithErrors(IDictionary<string, string[]> errors, string bag = "default")` also takes arrays of messages. FluentValidation is not automatically integrated into Minimal API `AddValidation()`. Call a registered `IValidator<T>` yourself and map its failures:

```csharp
app.MapPost("/users", async (CreateUserInput input, IValidator<CreateUserInput> validator) =>
{
    var result = await validator.ValidateAsync(input);
    if (!result.IsValid)
    {
        var errors = result.Errors.GroupBy(e => e.PropertyName)
            .ToDictionary(g => g.Key, g => g.Select(e => e.ErrorMessage).ToArray());
        return Back().WithErrors(errors);
    }
    return Results.Redirect("/users");
});
```

Import `FluentValidation` and register your validator. Supply client JSON field names in the dictionary when they differ from its property names.

## MVC

`AddInertiaMvc()` registers a global filter. An Inertia non-GET request with an invalid `ModelState` is redirected back with the errors before the action runs, in the bag from `X-Inertia-Error-Bag` (default `default`). `[ApiController]` controllers work too: their automatic 400 is replaced by the same redirect for Inertia requests.

```csharp
[HttpPost("/users")]
public IActionResult Store([FromBody] CreateUserInput input)
{
    if (!ModelState.IsValid) return ValidationProblem(ModelState);   // non-Inertia clients only
    db.Add(input);
    return Redirect("/users");
}
```

Binding failures get the generic message `The value is invalid.`, because their exception messages can expose internals.

## FastEndpoints

`c.ConfigureInertia()` adds a global pre-processor. A validation failure of an Inertia non-GET request becomes a redirect back with the errors; other requests keep FastEndpoints' 400 JSON. FluentValidation validators work as usual.

```csharp
public sealed class CreateUserValidator : Validator<CreateUserRequest>
{
    public CreateUserValidator() => RuleFor(x => x.Email).NotEmpty().EmailAddress();
}

app.UseFastEndpoints(c => c.ConfigureInertia(ep => ep.AllowAnonymous()));
```

`c.ConfigureInertia()` composes with an existing `c.Endpoints.Configurator`. Its optional callback runs after Inertia setup. The pre-processor runs after an endpoint's own pre-processors, so one that already answered (a 403, say) wins.

## Precognition (live validation)

[Precognition](/docs/precognition) validates a request without running the handler. Minimal APIs use `.WithInertiaPrecognition()` instead of `.WithInertiaValidation()`; FastEndpoints enables it with `ConfigureInertia()`. MVC does not support it.

## Error bags in the client

```tsx
const form = useForm({ name: '', email: '' })

<form onSubmit={(event) => {
  event.preventDefault()
  form.post('/users', { errorBag: 'createUser' })
}}>
  <input value={form.data.email} onChange={(event) => form.setData('email', event.target.value)} />
  <p>{form.errors.email}</p>
</form>
```

## All errors for a field

```csharp
builder.Services.AddInertia(o => o.WithAllErrors = true);
```

With the option on, `errors.email` is an array of every message instead of the first.

## State and redirects

Validation errors travel in the state store across the redirect. By default that is an encrypted cookie; it can be a session or MVC TempData instead. See [Flash data](/docs/flash-data) for the store choices and size limits.
