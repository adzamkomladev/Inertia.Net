Flash data is a message or value for the next page, such as “Contact saved.” Unlike shared props, it is not kept in browser history.

Inertia.Net carries flash data across the redirect and any further redirects. The next response that is not a redirect consumes it. Flash data appears as `page.flash`, and only when there is some.

```csharp
app.MapPost("/users", (CreateUserInput input, HttpContext context) =>
{
    context.Inertia().Flash("toast", new { type = "success", message = "Saved" });
    return Results.Redirect("/users");
});

// or on Back():
return Back().WithFlash("toast", "Saved");
```

```json
{
  "component": "Users/Index",
  "props": { "errors": {} },
  "flash": { "toast": { "type": "success", "message": "Saved" } }
}
```

On the client, read flash data from the page's `flash` or from the `onFlash` visit callback. The page's `flash` is `usePage().flash`, or `page.flash` in Svelte:

<Tabs>
  <Tab label="React">

```tsx
const { flash } = usePage()

{flash.toast && <Toast {...flash.toast} />}
```

  </Tab>
  <Tab label="Vue">

```vue
<script setup lang="ts">
import { usePage } from '@inertiajs/vue3'
import Toast from './Toast.vue'

const page = usePage()
</script>

<template>
  <Toast v-if="page.flash.toast" v-bind="page.flash.toast" />
</template>
```

  </Tab>
  <Tab label="Svelte">

```svelte
<script lang="ts">

  import Toast from './Toast.svelte'
</script>

{#if page.flash.toast}
  <Toast {...page.flash.toast} />
{/if}
```

<Callout type="info" title="Typed flash data">
The TypeScript generator can type `page.flash`. `FlashData<T>()` takes the whole flash object. For the `toast` above, use `record Flash(Toast? Toast)` and call `o.TypeScript.FlashData<Flash>()`. See [TypeScript types](/docs/typescript#flash-data).
</Callout>

Inertia forms keep their input on the client after `Back().WithErrors(...)`. They do not need a `WithInput()` helper. For a full-page form submission, choose only safe fields to flash before redirecting:

```csharp
return Back().WithFlash("old", new InertiaProps { ["email"] = email });
```

On the next page, read `flash.old` from the page and use the email to refill the field. Never flash passwords, tokens or other secrets.

## Remove a flash value

In a handler, call `http.Inertia().ForgetFlashed("toast", "user.name")` before rendering or redirecting.
This removes values set in this request or restored from a previous one. An exact key such as `"user.name"` wins over
the nested path. If no flash values remain, the page has no `flash` field. The remaining values still expire normally.

## Where state is kept

Some state must survive a redirect: flash data, errors, `clearHistory` and `preserveFragment`. When a request sets any of these and ends in a redirect, Inertia.Net saves the state in an `IInertiaStateStore`. The same applies when the request ends in a `Location()` / fragment `409`. Inertia.Net loads the state at the start of the next request. If the next request redirects again, the state is carried on, so `Back()` to a URL that itself redirects still shows the flash. Otherwise the response of the next request consumes the state. The state is also kept when the response is the version-mismatch `409`.

### Encrypted cookie (default)

The default store is an encrypted cookie named `.Inertia.State`. The cookie is protected with ASP.NET Core Data Protection, and it is `HttpOnly` and `SameSite=Lax`. The store works without sessions and under Native AOT. Tampered or undecryptable cookies are ignored and deleted. The store logs a warning when the cookie is larger than about 4 KB, because browsers drop larger cookies.

### Session store

```csharp
builder.Services.AddSession();
builder.Services.AddInertia(o => o.State.UseSession());

app.UseSession();       // before UseInertia
app.UseInertia();
```

Use the session store when flash data can be large or must not reach the browser, and you already run sessions.

### MVC TempData store

```csharp
builder.Services.AddInertiaMvc(o => o.UseTempDataStateStore());
```

This store keeps the state in MVC TempData, so the state follows your TempData provider. The provider is the default cookie provider, or `AddSessionStateTempDataProvider()` with `AddSession()` and `app.UseSession()` before `app.UseInertia()`. The store works for Minimal API endpoints too, because it saves TempData itself. It is not compatible with Native AOT.

### Your own store

Implement `IInertiaStateStore` and register it before `AddInertia`:

```csharp
public interface IInertiaStateStore
{
    ValueTask<byte[]?> LoadAsync(HttpContext httpContext);
    ValueTask SaveAsync(HttpContext httpContext, byte[] state);
    ValueTask ClearAsync(HttpContext httpContext);
}
```

The methods move opaque bytes. The format belongs to Inertia.Net.

## Choosing a store

| Store | Use when |
|---|---|
| Encrypted cookie | Default. Stateless, AOT safe, about 4 KB limit. |
| Session | Flash data can be large or must not reach the browser, and sessions already exist. |
| TempData | The app standardizes on MVC TempData, or you want to switch providers without changing code. |
| Custom | You need a shared store across instances or a different transport. |

<Callout type="warning" title="Multiple instances">
In a multi-instance deployment, configure Data Protection with a shared key ring. Otherwise the cookie written by one instance cannot be read by another.
</Callout>

## History flags

`encryptHistory` is written only when set and is not carried across redirects. `clearHistory` and `preserveFragment` go through the state store. They apply to the next page rendered after the redirects, and are then consumed.

```csharp
app.MapPost("/logout", (HttpContext context) =>
{
    context.Inertia().ClearHistory();
    return Results.Redirect("/login");
});
```

See [Redirects and history](/docs/redirects-and-history).
