Server-side rendering (SSR) renders the first visit on a JavaScript server, using your client bundle. Crawlers and slow devices then get HTML. Inertia XHR requests are never rendered on the server.

## 1. Build the SSR bundle

### Without the plugin

Write the server entry yourself (`ssr.tsx` for React, `ssr.ts` for Vue and Svelte):

<Tabs>
  <Tab label="React">

```tsx
// resources/js/ssr.tsx
import { createInertiaApp, type ResolvedComponent } from '@inertiajs/react'
import createServer from '@inertiajs/react/server'
import ReactDOMServer from 'react-dom/server'

createServer((page) =>
  createInertiaApp({
    page,
    render: ReactDOMServer.renderToString,
    resolve: (name) => {
      const pages = import.meta.glob<{ default: ResolvedComponent }>('./Pages/**/*.tsx', { eager: true })
      return pages[`./Pages/${name}.tsx`]
    },
    setup: ({ App, props }) => <App {...props} />,
  }),
  { host: '127.0.0.1', port: Number(process.env.INERTIA_SSR_PORT ?? 13714) },
)
```

Run the bundle with Bun or Node, or let the app start it:

```sh
bun ssr/ssr.js        # listens on http://127.0.0.1:13714
# or
node ssr/ssr.js
```

Build and run from a directory with `node_modules` installed. The SSR build leaves `node_modules` imports external.

## 2. Enable it

```csharp
builder.Services.AddInertia(o =>
{
    o.Ssr.Mode = SsrMode.Preferred;                  // Disabled (default), Preferred or Required
    o.Ssr.Urls.Add("http://127.0.0.1:13714");       // default when empty; add more servers to spread renders
    o.Ssr.ConnectTimeout = TimeSpan.FromSeconds(5);  // connection establishment
    o.Ssr.Timeout = TimeSpan.FromSeconds(5);         // total deadline per render
    o.Ssr.MaxPageBytes = 2 * 1024 * 1024;            // larger pages render on the client without a call
    o.Ssr.MaxResponseBytes = 16L * 1024 * 1024;      // success and error responses
    o.Ssr.BundlePath = "ssr/ssr.js";                 // skip SSR while this file does not exist
    o.Ssr.ExcludePaths.Add("/admin/*");              // exact, or a trailing * for a prefix
});
```

A response can choose its own mode:

```csharp
return Render("Checkout").WithoutSsr();
return Render("Landing").WithSsr(SsrMode.Required);
return Render("Admin/Home").WithSsr(SsrMode.Preferred);
```

The global mode decides first. When it is `Disabled`, SSR is off and no response can override that. Otherwise the response's mode wins, then `ExcludePaths`, then the global mode.

SSR runs only for first visits, which are the HTML responses. Inertia.Net posts the page JSON to `{url}/render`. The answer, `{ "head": [...], "body": "..." }`, is written into the root view. `@inertiaHead` outputs the head tags. `@inertia` outputs the body.

## 3. Let the app run Bun or Node

```csharp
o.Ssr.UseNodeProcess();          // also sets Mode = Preferred when it is Disabled
o.Ssr.UseNodeProcess(n =>
{
    n.BundlePath = "ssr/ssr.js";
    n.Executable = "node";
    n.Arguments.Add("--enable-source-maps");
    n.WorkingDirectory = null;                   // default: content root
    n.StartupTimeout = TimeSpan.FromSeconds(10);
    n.RestartOnExit = true;
    n.Instances = 1;                             // instance i listens on BasePort + i
    n.BasePort = 13714;
    n.LivenessInterval = TimeSpan.FromSeconds(5);
    n.LivenessFailureThreshold = 3;
    n.AllowNetworkExposure = false;
});
```

A hosted service runs `{Executable} {bundle}` once per instance. The executable is `node` by default, and Bun works too. The service logs stdout as Information and stderr as Warning under `Inertia.Net.Ssr`. It waits for every instance's `GET /health`. Occupied ports are refused before anything is spawned. `Ssr.Urls` is not used in managed mode, where the app runs the SSR process.

<Callout type="tip" title="Bun works too">
The executable is configurable. This documentation site builds a self-contained SSR bundle and runs it with Bun: `o.Ssr.UseNodeProcess(n => n.Executable = "bun")`. The default is `node`. The bundle accepts either runtime.
</Callout>

- An instance that exits is restarted after 1 second. The delay doubles up to 30 seconds.
- An instance that stops answering its liveness check is killed and restarted the same way.
- Shutdown stops the owned process trees without requesting `/shutdown`.
- Nothing is spawned while the Vite dev server runs.
- For external or remote servers, set `Mode` and `Urls` without `UseNodeProcess()`.

<Callout type="danger" title="Keep the SSR server on loopback">
The SSR server has no authentication. Anyone who can reach it can `POST /render`, which uses CPU, or `POST /shutdown`. Its `head` and `body` are written into your pages verbatim. Listen on `127.0.0.1`. Before an instance takes renders, Inertia.Net tries the machine's non-loopback addresses on the instance's port. If the instance answers there, Inertia.Net stops it and logs an error. `AllowNetworkExposure = true` keeps the instance running with a warning.
</Callout>

<Callout type="warning" title="Orphans">
A graceful shutdown stops the SSR process. If the .NET process is killed outright, the OS does not stop the SSR runtime with it. Use a process manager or container for hard-crash cleanup.
</Callout>

## 4. Development

When the Vite hot file is present (Development only), or `o.Vite.DevServerUrl` is set, Inertia.Net posts to `{viteDevUrl}/__inertia_ssr`. `@inertiajs/vite` serves this endpoint, so you need no built bundle and no separate SSR server.

```ts
import inertia from '@inertiajs/vite'

inertia({ ssr: { entry: 'resources/js/ssr.tsx', host: '127.0.0.1', port: 13714 } })
```

Use `ssr.ts` as the entry for Vue and Svelte.

`BundlePath` is ignored while the dev server runs.

## 5. Failures and fallbacks

### Send failures to monitoring

`Preferred` mode logs a failed render and lets the browser render the page. `Required` mode fails the request before any HTML is sent.
To send failures to monitoring, set the `o.Ssr.OnRenderFailed` callback during registration (fragment):

```csharp
builder.Services.AddInertia(o =>
{
    o.Ssr.Mode = SsrMode.Preferred;
    o.Ssr.OnRenderFailed = failure =>
        Console.Error.WriteLine($"SSR {failure.Type}: {failure.Component} at {failure.Url}");
});
```

The callback receives the error, type, hint, timestamp and any available stack or source information. It runs once for the
final failed attempt, before the fallback or the Required-mode exception. Keep the callback thread-safe. Do not show these
details to users, because renderer diagnostics may contain secrets. Policy skips, such as a missing bundle or an open circuit,
use logs and metrics.

In `Preferred` mode, every failure logs a warning and the page renders on the client. In `Required` mode, a failure throws `InertiaSsrException` before the first byte is written, so the app's exception handler can still answer.

After enough failures in a row, the app stops calling the SSR server for a while. It then probes the server before trusting it again:

| Type | Cause | Opens the circuit |
|---|---|---|
| `connection` | Connection refused or reset. A refused connection is retried on another server. | yes |
| `timeout` | `Ssr.Timeout` elapsed | yes |
| `http` | Non-2xx answer without a structured error | yes |
| `response` | Empty or malformed answer | yes |
| `render` | The component threw (structured error from the renderer) | no |
| `response-too-large` | Answer over `MaxResponseBytes` | no |
| `overloaded` | No render slot within `Concurrency.QueueTimeout`, or the queue is full | no |
| `circuit-open`, `not-ready`, `page-too-large`, `bundle-missing` | Skipped without a call | no |

**Circuit breaker.** The circuit breaker counts consecutive failures of the types that open the circuit. After `CircuitBreaker.FailureThreshold` of them (default 5), a server is skipped for `BreakDuration` (default 10 s). Then one render probes the server. If the probe succeeds, the circuit closes. If the probe fails, another break starts. A page that fails because of its own code never pauses the server.

**Render slots.** Each server takes at most `Concurrency.MaxActive` renders at once from this app instance. The default is 8, and `0` means no limit. Up to `MaxQueued` more renders (default 32) wait for a slot, each for at most `QueueTimeout` (default 250 ms). Renders that find no slot fall back immediately.

## 6. Several servers

```csharp
o.Ssr.Urls.Add("http://ssr-1:13714");
o.Ssr.Urls.Add("http://ssr-2:13714");
```

Each render goes to a server whose circuit is closed: the one with the fewest renders in progress. Ties rotate. Every server has its own slots, queue and circuit. Only a refused connection is retried on another server, within the same deadline.

Page props travel to the renderer, and the renderer's HTML goes into your pages unescaped. The renderer must therefore be trusted. A plain `http://` URL that is not loopback logs a warning at startup. Use HTTPS or a private network.

## 7. Health check

```csharp
builder.Services.AddHealthChecks().AddInertiaSsr();
app.MapHealthChecks("/health");
```

The health check reports what the renders have already shown. It does not call the SSR servers. It reports:

- healthy while SSR is disabled, while SSR goes through the Vite dev server, or while every server can take renders
- degraded while some circuits are open or some managed instances are not ready
- the registration's failure status (default unhealthy) when no server can take renders

The check's data lists each server's state.

## 9. Response cache

A render depends only on the page JSON. A page whose JSON is byte for byte the same for many visitors can reuse its HTML:

```csharp
builder.Services.AddInertia(o =>
{
    o.Ssr.Cache.Duration = TimeSpan.FromMinutes(5);
    o.Ssr.Cache.StaleFor = TimeSpan.FromMinutes(30);
    o.Ssr.Cache.MaxBytes = 64 * 1024 * 1024;
});

return Render("Pricing", props).WithSsrCache(TimeSpan.FromHours(1));
return Render("Pricing", props).WithSsrCache(TimeSpan.FromHours(1), staleFor: TimeSpan.FromDays(1));
```

The cache key is the SHA-256 of the page JSON (component, props, url, version and the rest). A new deploy or different props therefore never reuse a stale render. Pages with per-user props make one entry per user, so cache the pages that are shared. A cache hit is counted as `inertia.ssr.outcomes{inertia.ssr.outcome=rendered, inertia.ssr.reason=cache}` and bypasses the render slots and circuit breakers. Nothing is cached while the Vite dev server renders.

Concurrent misses for the same page share one fill per app instance. Waiting counts against `Ssr.Timeout`. Cancelling a waiting request does not cancel the request that fills the entry.

With `StaleFor`, a render past its `Duration` is still served. The bounded background worker refreshes it after the response completes, like stale props. The connection can accept its next request while the renderer runs. Refreshes cancel when the host stops. If the 64-entry queue is full, the refresh is dropped and logged. Monitor `inertia.cache.refresh.dropped` with `inertia.cache.kind=ssr`. `IInertiaCache.ClearSsrAsync()` removes every render.

`Ssr.ConnectTimeout` limits the time to establish a connection, independently of `Ssr.Timeout`. Both accept a positive duration or `Timeout.InfiniteTimeSpan`. In Required mode, `InertiaSsrException.Message` contains a generic failure category suitable for an error page. Renderer diagnostics remain in application logs and diagnostic exception properties. Do not expose those properties to clients.

## Connection timeout and cached renders

`Ssr.ConnectTimeout` defaults to five seconds and limits the time to establish a connection. `Ssr.Timeout` limits the entire render. In `Required` mode, exceptions use a generic public message. Diagnostic properties can contain private renderer details, so do not display them to users.

A stale SSR cache hit returns immediately and schedules a refresh on a bounded background worker. The worker's queue holds 64 pending refreshes. A dropped refresh logs a warning and increments `inertia.cache.refresh.dropped` with `inertia.cache.kind=ssr`. Cached prop loaders used with stale refresh must use singleton dependencies or create their own scope. Never capture request-scoped services or `HttpContext`. Global `Ssr.Cache.Duration` is suitable for anonymous pages. Prefer per-page `WithSsrCache` and keys that account for all user and tenant data.
