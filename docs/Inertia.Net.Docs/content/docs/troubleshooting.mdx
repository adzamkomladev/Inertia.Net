## `Inertia.Render(...)` does not compile

The compiler reports `'Inertia' is a namespace`. Call `Render(...)` without a namespace or class prefix. The namespace `Inertia.Net` shadows the class name outside the `Inertia.Net` namespace.

The global usings come from the package's `buildTransitive` props and need `<ImplicitUsings>enable</ImplicitUsings>`. Without implicit usings, or with `InertiaNetImplicitUsings` set to `false`, add `using static Inertia.Net.Inertia;`.

<Accordion>
  <AccordionItem title="Generated code fails with 'Inertia' is a type">
    Inside a namespace that starts with `Inertia.Net.`, the name `Inertia` binds to the `Inertia.Net.Inertia` class. Source generators that emit non-`global::` names starting with `Inertia` then break. Do not put your app's code under an `Inertia.Net.*` namespace.
  </AccordionItem>
  <AccordionItem title="Vite manifest not found. Looked in: ...">
    Do one of these three things. Run your package manager’s build script (`npm run build`, `bun run build`, `pnpm run build` or `yarn run build`). Or start the dev server so that the hot file exists in Development. Or set `o.Vite.ManifestPath` / `o.Vite.BuildDirectory`. Check that Vite writes `.vite/manifest.json` (`build.manifest: true`, Vite 5 and later) to `wwwroot/build`. Also check that the build output is part of what you deploy.
  </AccordionItem>
  <AccordionItem title="Vite entry '...' was not found in the manifest">
    The `@vite("...")` argument must equal the manifest key, which is the path relative to the Vite root. The error lists the available entries.
  </AccordionItem>
</Accordion>

## TypeLoadException for `IValidatableInfo` on .NET 11

`Could not load type 'Microsoft.Extensions.Validation.IValidatableInfo'` (or `ValidatableTypeInfo`) means a .NET 10 build is running on .NET 11. Upgrade every Inertia.Net package to 1.8.0 or later and target `net11.0`. Do not roll a `net10.0` app forward to the .NET 11 runtime. See [Installation](/docs/installation).

## My 404 shows the Inertia modal in production

Register `AddInertiaErrorPages()` and call `UseInertiaErrorPages()` before `UseInertia()`. Create your error components. See [Error pages](/docs/error-pages).

## Form submissions fail with 419

`UseInertiaAntiforgery()` rejected a request without a valid `X-XSRF-TOKEN`. Check these points:

- The page was loaded through the middleware. The middleware sets the `XSRF-TOKEN` cookie.
- The cookie reaches the browser. A `Secure` cookie on plain HTTP is dropped. See [Deploying](/docs/deploying).
- All instances share the Data Protection key ring.
- `UseAuthentication()` runs before `UseInertiaAntiforgery()`.

A sign-in or sign-out changes the token. After one, reload the page, or return `Back()` from `OnRejected`. Exempt webhooks and token-authenticated APIs with `.DisableAntiforgery()` or `ShouldValidate`.

## The Inertia page component was not found

This error means that `o.Pages.Directory` is set and the component passed to `Render(...)` has no page file in that directory. Names match exactly, as the client's page resolver does, even on case-insensitive file systems. The message suggests the closest page. Fix the name, or check `Pages.Extensions` when your pages use another extension. The check runs only in Development.

## A redirect to another site turns into a 409

This is the `ConvertExternalRedirects` option, which is on by default. An Inertia request cannot follow a redirect to another origin. Instead, the request gets `409` + `X-Inertia-Location` and the client does a full visit.

If this happens for your own host, the app is behind a proxy that does not forward the scheme. See [Deploying](/docs/deploying), or use relative redirects. To disable the conversion, set `o.ConvertExternalRedirects = false`.

## The root view resolves outside the content root

`RootView` and `WithRootView(...)` take a path relative to the content root. Absolute paths and `..` are refused. Never derive these paths from request data.

## The page keeps reloading, or a request loops with 409

A `409` means the asset version differs between the client and the server. A loop means the two versions never match. Usually the version changes on every request: a `VersionResolver` returns a new value each time, or a file watcher regenerates the manifest. Another usual cause is that different instances behind a load balancer serve different builds. Use a stable version string.

In Development the manifest hash changes after each `vite build`, which is expected once.

## A blank page at localhost:5173

`http://localhost:5173` is the Vite dev server. It serves assets and hot-reload updates to your app. It has no pages of its own, so it shows a blank page. Instead, open the ASP.NET Core URL that `dotnet watch` or `dotnet run` prints. In the starter templates that URL is `http://localhost:5180`.

## The dev server tags do not appear

Inertia.Net reads the hot file only when `ASPNETCORE_ENVIRONMENT=Development`. Check that `wwwroot/hot` exists and contains `http://localhost:5173`, or set `o.Vite.DevServerUrl`. Also set `base: '/'` for the dev server in `vite.config`.

## The root template was not found, or @inertia is missing

`RootView` is relative to the **content root**. Copy `app.html` to the output and publish directories (`CopyToOutputDirectory`, `CopyToPublishDirectory`). The template must contain `@inertia`.

## Flash data or errors disappear

Browsers limit the state cookie to about 4 KB. Flash less data, or use `o.State.UseSession()`. If the app runs on several instances, share Data Protection keys.

If the browser never sends the cookie back, check the cookie's `Secure` flag when the app runs on HTTP behind a proxy that does not forward `X-Forwarded-Proto`.

## Validation errors do not show up (Minimal API)

Use `.WithInertiaValidation()` on the endpoint. Without it, the built-in `AddValidation()` filter returns a `400` problem details response that the Inertia client cannot use. Make sure the model types are `public`.

## Validation keys do not match my field names

Keys use dotted indices and available JSON member aliases. Minimal API and MVC use the page serializer’s HTTP JSON options. FastEndpoints uses its binding serializer policy. Keep these aligned with client field names. Metadata-free or custom resolver paths can fall back to naming-policy conversion. See [Validation](/docs/validation-and-errors).

## InertiaProp values can only be serialized by Inertia.Net

An `InertiaProp` is in a place that Inertia.Net does not walk:

- a `Flash(...)` value
- a read-only dictionary type that does not implement `IDictionary`
- a type with a custom converter

Inertia.Net walks lists, typed dictionaries (`Dictionary<TKey, TValue>` with any key type), `object` members and `IDictionary<string, object?>`. Put props in `InertiaProps`, or declare the member as `InertiaProp` (or `object`) on the typed page object.

## Native AOT: JsonTypeInfo metadata was not provided

Add the type to your `JsonSerializerContext` and chain it with `ConfigureHttpJsonOptions`. To find these errors early, set `JsonSerializerIsReflectionEnabledByDefault=false` in regular builds. See [Native AOT](/docs/native-aot).

## SSR does not run and there is no error

SSR falls back to client rendering on any failure. Look for the warnings `Inertia SSR failed (...)` and `Inertia SSR skipped (...)`. The first includes the server's hint.

Check these points:

- `o.Ssr.Mode` and `Urls`.
- The Node server is running (`GET /health`). With `UseNodeProcess()`, look for `Inertia.Net.Ssr` log lines.
- `BundlePath` points at the built file.
- The path is not in `ExcludePaths`.
- The page is under `MaxPageBytes`.

To see the failure, set `Mode = SsrMode.Required` in Development.

## SSR skipped (circuit-open) or (overloaded)

- `circuit-open`: the server failed `CircuitBreaker.FailureThreshold` times in a row and is skipped for `BreakDuration`. The earlier `Inertia SSR failed` warnings say why.
- `overloaded`: more renders arrived than `Concurrency.MaxActive` plus `MaxQueued`, or one waited longer than `QueueTimeout`. Add servers or instances, or raise the limits if the server has spare capacity.

## Several managed instances never become healthy

Every instance must listen on its own port. For that, the SSR entry has to read `process.env.INERTIA_SSR_PORT`. A bundle built only by `@inertiajs/vite` listens on the port that was fixed at build time.

## The SSR output is not hydrated

Use the hydrating client entry shown in [Server-side rendering](/docs/server-side-rendering) and build both bundles from the same sources. The SSR body is marked `data-server-rendered="true"`.

## Does it work behind a path base?

Yes. The page `url` keeps the path base, the Vite URLs include it, and `Back()` works.

## Can I use Newtonsoft.Json?

No. Props use System.Text.Json with the HTTP JSON options.

## Can I mix Razor Pages or views with Inertia pages?

Yes. Inertia handles only the endpoints that return `Render(...)`. The middleware leaves other responses alone, apart from `Vary: X-Inertia`.

## Forms submit invalid data

Minimal API endpoints need `.WithInertiaValidation()` or `.WithInertiaPrecognition()` and `AddValidation()`. Endpoint construction throws when validation resolvers are missing. Routing can construct endpoints lazily. See [Validation](/docs/validation-and-errors).

## 419 in tests

1. Use a cookie-preserving client.
2. Load an Inertia page first.
3. Use `request.WithXsrfToken(pageResponse)` on the form request.

See [Testing](/docs/testing#testing-a-form-with-antiforgery).

## Precognition: login locks users out while typing

Precognitive POSTs pass through rate limiting. Use separate bounded partitions for validation and for submission, and validate on blur. See [Precognition](/docs/precognition#rate-limiting). A throttled validation still rejects, so show a retry message. To render a custom Inertia error page for a real submission rejected with 429, add 429 with `AddInertiaErrorPages(o => o.StatusCodes.Add(429))` and put `UseInertiaErrorPages()` before `UseRateLimiter()`. Precognitive JSON responses keep their 429 and `Precognition: true` header.

## 'Location' is a type but is used like a variable

The imported static `Location` name may collide with a type. Call `Inertia.Net.Inertia.Location(url)` explicitly, or opt out with `<InertiaNetImplicitUsings>false</InertiaNetImplicitUsings>` and add your own imports. See [Configuration](/docs/configuration#name-collisions).

## A cached prop loader runs every request

Check that the key and duration are stable and the cache store works. Dot-key props support caching. Include every user or tenant dependency in the cache key. A stale refresh needs its own scope and may be dropped when the background queue is full. See [Props](/docs/props#cached-props).
